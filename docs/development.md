# Процесс разработки

## Поколения backend

`releaseVersion` — версия пакета расширения. `backendGeneration` — постоянный ID
контракта и Firebase backend; совместимые релизы используют прежнее поколение.
`createdWithVersion` — версия расширения в момент создания комнаты, она не меняется
при обновлении клиента или смене видео. Равенство версий участников не требуется.
Совместимость объявляет оператор через `new|reuse`, номер версии её не определяет.

Строгие схемы в `src/lib/backend-generations.ts` проверяют инвентарь, release descriptor
и публичный реестр. Реестр содержит только поколения, первые версии и active/retired;
он не задаёт backend URL. Retired необратим, его отметка сохраняется при откате Hosting.
У документа нет ежедневного TTL: ограничивается свежесть локального чтения, а не возраст
постоянной отметки. Инвентарь различает сведения runbook, fixtures и наблюдения live
с датой проверки; сведения репозитория не доказывают текущее состояние облака.

`scripts/generation-rules.mjs` генерирует контракт для явно заданного нового
поколения. Эмулятор использует `emulator-v1`. Для повторного выпуска существующего
поколения используются сохранённые Rules и schema с проверенными SHA-256;
генерация из текущего дерева не заменяет его снимок.
Первый descriptor явно содержит `previous: null` и готовится через
`release:prepare -- initial` только при отсутствии истории. Следующие `new|reuse`
требуют настоящий предыдущий descriptor; имена поколений не имеют особого смысла.
Локальная проверка Auth/Rules: `npm run test:integration`; production она не меняет.

Каталог и session bindings используют namespace с backendGeneration и версией
локального формата 2. Patch-релиз с прежним поколением сохраняет эти ключи;
прежние namespace не читаются и не мигрируют. Сообщения session/tab/catalog без
собственного поколения отклоняются, даже при совпадении room key. После несовместимого
обновления открытое видео остаётся локальным: для совместного просмотра требуется
новое явное создание/вход. При invalidation runtime адаптер останавливается и панель
удаляется; отложенные команды не переносятся в новую сессию.

## Роли документов

- PRD.md: цель продукта, сценарии, границы и критерии приёмки MVP.
- openspec/specs/: согласованное поведение завершённых изменений.
- openspec/changes/<change>/specs/: предлагаемые изменения поведения.
- docs/adr/: существенные архитектурные решения с причинами и статусом.
- design.md внутри change: устройство конкретного изменения.
- tasks.md внутри change: незавершённая работа с проверяемым результатом.

PRD не дублирует детальные требования specs. ADR не заменяет сценарии. Прототип принят 2026-11-03; его требования перенесены в основные specs, change архивирован. Последующие изменения начинаются с нового proposal.

## OpenSpec Refinement

Для новых changes по умолчанию используется локальная schema `product-refined`
версии `v0.4.0`: она уточняет продуктовую постановку в proposal, поведение в specs
и технические решения в design. Обычный workflow OpenSpec остаётся прежним.
Инструкции и шаблоны хранятся в `openspec/schemas/product-refined/`, исходный тег
и commit — в `REFINEMENT_VERSION` внутри этой папки. Источник на машине разработчика:
`<openspec-refinement-checkout>`; установленная копия работает независимо
от наличия исходного репозитория. Лицензия upstream сохранена в `LICENSE.upstream`.

Настройка `schema` в `openspec/config.yaml` применяется к новым changes.
У существующих changes приоритет имеет schema в их `.openspec.yaml`;
они не переключаются автоматически. Проверка подключения:

```sh
npm exec -- openspec schema which product-refined
npm exec -- openspec schema validate product-refined
```

Для обновления подготовь schema из нового release-тега отдельно, сравни её
с установленной копией с учётом локальных правок, затем замени файлы, обнови
`REFINEMENT_VERSION` и повтори проверку. Сгенерированные `.agents/skills/`
вручную не редактируются. Статусы Refinement Draft/Ready направляют работу агента,
но не блокируют переходы CLI автоматически.

## Цикл изменения

1. Explore при неопределённости: исследуем код и ограничения, формулируем задачу.
2. Propose: proposal.md описывает проблему, границы и затрагиваемые capabilities.
3. Specs и design: фиксируем наблюдаемое поведение и способ его реализации.
4. Tasks: разбиваем работу на проверяемые шаги.
5. Apply: реализуем задачи, добавляем необходимые проверки и обновляем документы.
6. Review и verification: проверяем сценарии, typecheck, сборку и подходящие тесты. Для интеграции с YouTube сохраняем реальные наблюдения.
7. Sync и archive: переносим delta specs в основные specs и архивируем завершённое изменение. При штатном CLI archive синхронизация может выполняться самим архивированием; повторно применять дельты не нужно.

Незаполненный checkbox означает оставшуюся работу. Создание документов не означает готовность реализации. Не архивируем change с невыполненными проверками.

## Совместимость версий

Решение пользователя от 2026-11-03: обратная совместимость с предыдущими версиями не требуется. При изменении схем данных, протоколов и локального хранения поддерживаем только актуальный формат. Не добавляем миграции, чтение старых форматов и fallback исключительно ради прежних версий. Старые сборки и данные не обязаны работать с новой версией; breaking changes явно отмечаем в change. Это правило действует для следующих изменений, пока пользователь не пересмотрит его.

## Команды проекта

```sh

npm run build
npm test
npm run test:e2e
npm run test:integration
npm run test:firebase-context

```

AI-инструкции OpenSpec генерируются в .agents/skills/. Перед применением конкретного workflow читаем соответствующий SKILL.md. Точные команды интеграции зависят от установленной версии CLI; openspec init показывает поддерживаемый способ вызова.

Unit-тесты находятся рядом с кодом (`src/**/*.test.ts`), проверки эмуляторов — в `tests/integration/`, браузерные проверки — в `tests/e2e/`. Playwright использует собственный Chromium с отдельным временным persistent profile. Начальный smoke-тест проверяет загрузку MV3 и popup как extension page; он не подтверждает управление YouTube или поведение настоящего popup при закрытии.

`npm run test:integration` требует JDK 21+, запускает Auth/RTDB/Hosting с demo-проектом и останавливает их после тестов. Launcher `scripts/firebase.mjs` находит Java в PATH, JAVA_HOME или стандартном каталоге Homebrew, не меняя системную конфигурацию. Локальные порты и ограничения Rules описаны в README.

`npm run test:firebase-context` отдельно собирает `experiments/firebase-context/` в `.output/firebase-context/chrome-mv3` и запускает матрицу из `tests/firebase-context/` под эмуляторами: два profiles, общий UID, настоящий popup, принудительная остановка worker, reload и восстановление данных. Его Playwright config отделён от обычного smoke. В обычную сборку эти entrypoints и loopback permissions не входят. Выбранный контекст описан в ADR-0002; это пока стенд, а не реализация room transport.

`npm run test:player` собирает `experiments/youtube-player/` и запускает управляемый DOM/media-стенд. `npm run test:player:youtube` отдельно запускает opt-in матрицу настоящего YouTube, в том числе ограниченное наблюдение естественной рекламы; отсутствие рекламы означает skipped. Live-тест требует сети и не входит в обычный E2E. Подтверждённые наблюдения и непроверенные сценарии фиксируются отдельно в журнале; skipped не закрывает задачу. Командный протокол диагностики и ручная проверка описаны в `experiments/youtube-player/README.md`.

Файлы `autoplay.spec.ts` и `youtube-autoplay.spec.ts` используют настоящую browser policy и отключают trace: DOM snapshots и обычные page/locator evaluations в используемой версии Playwright дают user activation. До отказа `play()` состояние проверяется только extension messages и CDP без user gesture. В остальных player-сценариях trace при ошибке сохраняется.

`npm run test:transport` проверяет основной `src/` с локальным флагом, без отдельных экспериментальных entrypoints. Output — `.output/room-transport/chrome-mv3`. Два profiles проверяют общий UID внутри профиля, настоящий popup, подписки при остановленном worker, reload, очистку и HTTP-отказ Auth с повторной попыткой. Исходная lifecycle-матрица использует временные read-only fixture Rules. Матрица создания комнаты использует продуктовые Rules и проверяет play/pause, позицию, скорость, clipboard, повторное открытие popup, рекламу/загрузку и отказ записи. Для отказа временно запрещаются все записи; обе матрицы восстанавливают исходные Rules, файл репозитория не меняется. Trace отключён, чтобы не записывать Auth/room messages. `YOUTUBE_TRANSPORT_REAL=1 npm run test:transport` добавляет сетевые проверки iframe/Auth и создания комнаты из настоящего YouTube; обычный запуск явно пропускает live-сценарии.

`tests/room-transport/invitation.spec.ts` проверяет вход по приглашению во втором независимом profile, разные UID, чтение и обновления под продуктовыми Rules, повреждённую ссылку, отсутствие комнаты, отказ доступа и повтор, инструкцию без расширения и ограничение origin/порта/пути. Секрет передаётся из isolated content script только во встроенный extension iframe через строго проверенные runtime messages; ответ hosting-bridge содержит только подтверждение доставки. До явного нажатия входа Auth не запускается. Изменение fragment снимает предыдущую подписку. Матрица также проверяет перенос сессии во вкладку просмотра, повторное приглашение после остановки worker и восстановление после reload. `tabs.spec.ts` проверяет одновременные приглашения, закрытие вкладки, выход и отказ постороннему session iframe; `presence.spec.ts` подтверждает одно соединение при повторном приглашении в профиле создателя. Sync engine подключён в задаче 3.3. Матрица `restrictions.spec.ts` проверяет локальные ограничения и восстановление в двух profiles; `reconnect.spec.ts` проверяет offline, получение актуального состояния перед sync и обрыв транзакции до доставки серверу/до ack. Autoplay проверяется через CDP без user gesture в watch-документе и extension iframe, с отключённым trace. Реклама/waiting видеостенда не считаются подтверждением естественной рекламы YouTube.

`tests/room-transport/local-settings.spec.ts` проверяет громкость/mute, субтитры и выбранное качество в двух независимых profiles: личные действия не меняют playback комнаты и настройки другого участника, последующий общий seek сохраняет личные настройки. По умолчанию используется видеостенд; `YOUTUBE_TRANSPORT_REAL=1` добавляет настоящий YouTube с обычными контролами. Регрессионный player-тест отдельно проверяет, что клавиши личных контролов не разрешают системные seek/play/pause как общие команды.

`tests/room-transport/sync.spec.ts` — сквозной сценарий 4.1: создание через настоящий popup, вход по приглашению в независимом profile, два разных UID из собственных popup и server presence. Play/pause, seek и скорость проверяются в обе стороны с точным авторством и одной revision на действие; seek сверяется с ожидаемой позицией на сервере и в обоих плеерах. После выхода создателя гость продолжает управление. JSON-приложение содержит media samples и результат сравнения UID без самих идентификаторов и секретов. Целевой запуск и наблюдения приведены в журнале эксперимента; настоящий YouTube включается отдельно и не подменяется результатом видеостенда.

`tests/room-transport/youtube-matrix.spec.ts` добавляет opt-in матрицу настоящего YouTube: popup/worker/reload, SPA, конфликт команд, offline/reconnect, настоящее buffering и обрыв транзакции до сервера/до ack. Сетевые перехваты управляют только доставкой, не подменяя SDK, команды, media events или Rules. `youtube-ads.spec.ts` наблюдает естественную рекламу при входе гостя в видимых Chrome-профилях; нужен графический сеанс. Отсутствие рекламы — skipped, незавершённый setup — ошибка. Оба файла включаются только при `YOUTUBE_TRANSPORT_REAL=1`; условия, результаты и команда целевого запуска — в журнале. Снимки без UID/секретов и этап setup сохраняются в JSON-приложения.

`npm run test:cloud` использует `.env.cloud`, отдельную сборку `.output/cloud/chrome-mv3`, настоящий YouTube и тестовый облачный Firebase. `tests/cloud/playback.spec.ts` планирует от 32 до 128 команд в двух независимых профилях: от trusted input до устойчивого применения media у второго участника, позиции через 3 секунды и отсутствие лишних revision. Метрики сохраняются и при падении; эмуляторный прогон явно помечается rehearsal. Несколько сессий с одинаковыми условиями объединяет `scripts/summarize-cloud.mjs`, сохраняя все исключённые случаи и незавершённые прогоны. Чистая обработка измерений дополнительно проверяется Vitest. Подготовка проекта, deploy Auth/Rules/Hosting, методика и границы — в [инструкции](experiments/cloud-measurement.md).

`npm run probe:youtube-delivery` — отдельный контроль на настоящем YouTube без расширения/Firebase: переход на 45 с и наблюдение доставки 36 секунд. Exit 1 и отчёт означают, что доставка прервалась. Это диагностика среды, не критерий исправности расширения. `YOUTUBE_DELIVERY_REAL=1 npm run test:player` проверяет распознавание естественно возникшей ошибки и восстановление адаптера после reload; нужен воспроизводимый внешний сбой. Его отсутствие в другом окружении не доказывает регрессию. Естественная реклама по решению пользователя отложена за пределы приёмки текущего прототипа; стендовые проверки локальности сохраняются.

Для сравнения режимов: `CLOUD_HEADLESS=0 npm run test:cloud` запускает два видимых окна. Для контроля в установленном Chrome: `YOUTUBE_PROBE_CHANNEL=chrome YOUTUBE_PROBE_HEADLESS=0 npm run probe:youtube-delivery`. Профили временные, параметры и версии сохраняются в JSON. Все эти запуски управляются Playwright, включая видимый установленный Chrome. Они по-прежнему воспроизводят внешний сброс media. Итоговая [приёмка в обычном Chrome](experiments/youtube-native-acceptance-2026-11-03.md) с независимыми тестовыми наблюдателями завершена: 48 команд, 31 пригодный замер, p95 228 мс, максимум расхождения 0,178 с, без эха. Методика QA-сборки и пересчёт сырых данных описаны в [инструкции](experiments/cloud-measurement.md#наблюдение-в-обычном-chrome).

Скорость применяется через отдельный MAIN-world content script; DOM-запрос содержит лишь videoId/числовую скорость. Прямой `video.playbackRate` оставляет внутреннюю скорость YouTube устаревшей. `tests/player/youtube-rate.spec.ts` проверяет нативное меню и английские/русские клавиши после remote apply (`npm run build:player-probe`, затем `YOUTUBE_PLAYER_REAL=1 npx playwright test --config playwright.player.config.ts youtube-rate.spec.ts`). Сквозной `sync.spec.ts` проверяет их у обоих получателей, авторство и одну revision на действие; `YOUTUBE_TRANSPORT_REAL=1` включает настоящий YouTube. `tests/keyboard.ts` передаёт trusted key/code русской раскладки, не меняя системную раскладку. MAIN-методы watch-страницы не гарантированы официальным iframe API, поэтому успешный стенд не заменяет эту live-проверку.

## Порядок работы

Архивированное изменение [natural-seek-order](../openspec/changes/archive/2026-11-03-natural-seek-order/verification.md) добавляет подтверждение перемотки по pointerup/keyup, trailing debounce, защиту активного жеста и порядок по времени действия в серверных часах. `tests/room-transport/seek-order.spec.ts` проверяет два независимых profiles: чужой seek во время удержания/drag, последнее локальное действие во время незавершённой транзакции и обратную доставку. WebSocket-перехват задерживает исходный пакет настоящего SDK; новые media events, команды и продуктовые Rules остаются настоящими. Это видеостенд; live-приёмку с новой сборкой и обновлёнными облачными Rules выполняем отдельно. Схема обязательных меток и ограничения часов описаны в README и design этого change.

Последующая [live-проверка natural-seek-order](experiments/youtube-seek-order-acceptance-2026-11-03.md) завершена: пять облачных команд в обычных профилях Chrome без эха, защита удержания/drag и порядок конфликтов подтверждены отдельными YouTube-тестами. Дальний seek автоматизированного Chromium ограничен загрузкой media; контроль без расширения и Firebase также неуспешен. Новый opt-in `youtube-seek-order.spec.ts` входит в `YOUTUBE_TRANSPORT_REAL=1 npm run test:transport`.

Первое изменение `youtube-sync-prototype` завершено и архивировано; PRD уточнён, ADR-0002/0003 приняты для технического прототипа. Список комнат и [явная смена видео](../openspec/changes/archive/2026-11-03-room-video-switch/verification.md) также завершены и архивированы. Смена сохраняет единственную связанную вкладку комнаты; обычная навигация остаётся локальной до возврата или подтверждённого предложения своего видео. Дальнейшие границы определяем по PRD.

Для воспроизводимых локальных проверок используется Emulator Suite. Облачные измерения выполнены на отдельном тестовом проекте `example-qa`; результаты и незавершённые длинные сценарии приведены в журнале 4.3. Публикация расширения выполняется отдельно.

## Ограниченное подключение и бюджет соединений

С версии 0.2.0 попытка включает статус Hosting (до 3 с), Auth, связь и свежий REST GET;
общий предел — 15 с. Один владелец выполняет до четырёх повторов с задержками
10/20/40/60 с и jitter 0–20%. На cooldown он приостанавливает свой SDK socket.
«Остановить попытки» сохраняет binding, каталог и detached-режим; «Повторить подключение»
начинает новую серию. Выход из комнаты — отдельное действие. Offline-действия не ставятся
в очередь; до свежего чтения запрещены отправка и применение общего управления.

Проверка приглашения и закрытой записи каталога — REST с прежним Firebase ID token и
прежними Rules; дополнительный Firebase App/RTDB socket не создаётся. Уже связанную
вкладку сначала активирует background без Auth/REST. Popup отображает состояние
watch-документа, не создавая собственного Auth ради его статуса. Закрытие popup
отменяет только его read-only вход. Operation ID проверяется background перед открытием
новой вкладки; поздние результаты отменённой операции не должны открывать просмотр.

`capacity.spec.ts` считает живые realtime WebSocket на watch-документ и отсутствие сокетов
у read-only приглашения. `reconnect.spec.ts` задерживает REST, сохраняя реальный SDK,
Auth, Rules и проверки до/после ack. Trace отключён: REST URL содержит ключ и ID token.
Эмуляторный socket-счётчик подтверждает поведение клиента в данной среде, но не реальное
списание Firebase квот, стоимость REST или работу настоящего YouTube.

Здоровая watch-сессия не опрашивает реестр и статусы. Подключение и восстановление
используют общий бюджет 15 секунд. Watch держит один realtime socket, а чтение при
входе из приглашения и каталога использует HTTPS REST без realtime socket. Presence
создаётся после проверки свежего состояния комнаты. Операторские команды и порядок
публикации описаны в [runbook выпуска](release.md).
