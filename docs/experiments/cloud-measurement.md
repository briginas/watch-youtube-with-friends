# Облачные измерения прототипа

Итоговая приёмка 2026-11-03 завершена в обычном Chrome: 48 команд, 31 пригодный замер, p95 227,90 мс, максимум расхождения 0,17791 с, без эха. [Отчёт и исходные данные](youtube-native-acceptance-2026-11-03.md). Автоматизированные попытки ниже сохранены как отдельные результаты и не объявляются успешными.

Критерии PRD: p95 от команды до применения у второго участника ≤1 с, минимум 30 команд; расхождение позиций ≤0,5 с через 3 с после команды при готовых плеерах. Итоговые значения и ограничения записываются в [журнал](youtube-sync-prototype.md). Успешная проверка сценария на эмуляторе не закрывает 4.3.

## Подготовка

Нужен отдельный тестовый Firebase-проект с Web App, Anonymous Auth, Realtime Database и Hosting. Вход CLI: `node node_modules/firebase-tools/lib/bin/firebase.js login`. Если Firebase требует MFA Google или принятие Terms of Service, владелец аккаунта выполняет эти шаги сам.

1. Создать тестовый проект либо добавить Firebase к уже созданному Google Cloud-проекту.
2. Зарегистрировать Web App и создать default RTDB в выбранном регионе. CLI `database:instances:create` создаёт дополнительные базы, первая создаётся через `firebase init database` либо Firebase Console.
3. Скопировать `.env.example` в `.env.cloud`, заполнить публичные Web App settings и условия сети/расположения клиентов. Не добавлять service account или административные токены в `WXT_*`: эти переменные входят в расширение.
4. Выполнить `npm run deploy:cloud`: разворачиваются Rules и статическая страница приглашения, включается Anonymous Auth в указанном тестовом проекте. Контракт комнат берётся из существующих проверенных Rules, `_probes` в облако не попадает. Настройка провайдера следует [документации Firebase CLI](https://firebase.google.com/docs/auth/configure-providers-cli).
5. Выполнить `npm run test:cloud`. Сценарий использует настоящий YouTube и два новых независимых Chromium-профиля. Сборка находится в `.output/cloud/chrome-mv3`.

Команды требуют Node 24. Для сборки облачного расширения без замеров: `npm run build:cloud`. `.env.cloud` исключён из Git. Пустая конфигурация сохраняет прежнее поведение обычной сборки без сервера; `WXT_FIREBASE_EMULATORS=1` всегда выбирает локальный demo-проект.

По умолчанию сценарий работает в headless Chromium. `CLOUD_HEADLESS=0 npm run test:cloud` открывает два видимых окна; значение сохраняется в `environment.headless`. `CLOUD_VIDEO_URL` выбирает другой обычный записанный ролик. Прогоны с разными роликами или режимами браузера нельзя объединять в одну выборку через `summarize-cloud.mjs`.

## Методика

Сценарий создаёт комнату через popup, входит по настоящему приглашению и подтверждает разные UID. Затем выполняет минимум 32 действия через trusted keyboard/pointer input: серии по восемь команд с чередованием инициатора. Если после четырёх серий ещё нет 30 замеров без локальных ограничений, выполняются дополнительные серии, максимум 128 команд. Исключённые случаи сохраняются. В каждой серии есть play, pause, seek в обе стороны и скорость 1/1,25, включая команды во время воспроизведения. Popup и страница приглашения закрыты; отдельные extension-документы читают существующий status API после каждого замера для проверки revision/авторства. Они не отправляют общие команды.

Время начала — capture-событие реального ввода, включая debounce seek. Оба плеера снимаются каждые 10 мс по монотонным browser clocks, приведённым к общей временной шкале хоста. Конец применения — совпадение состояния, скорости и прогнозируемой позиции второго плеера с состоянием источника в течение 100 мс, при готовом media. Допуск совпадения позиции — 0,5 с, как у адаптера. Время опроса SDK и сетевого REST-запроса в метрику не входит. Пропуск между снимками более 100 мс разрывает интервал устойчивого применения.

Для сравнения позиций берутся первые независимые снимки не раньше `input+3000ms`. Они приводятся к более позднему времени по скорости воспроизведения; задержка снимков и разница времён сохраняются отдельно. Задержка более 50 мс относительно требуемой секунды делает замер непригодным. Команды с рекламой или `readyState<3` в первые 3 секунды либо неготовыми плеерами при снимке отмечаются отдельно от выборки стабильной работы. Неприменённые за окно наблюдения команды имеют `latencyMs: null`, не считаются успешными; число полученных и применённых команд приводится явно, p95 всей выборки в таком случае не выдаётся. p95 вычисляется методом ближайшего ранга `ceil(0.95*N)`.

JSON лежит в `.output/cloud/test-results/**/measurements.json` и не содержит ключей комнат, UID, приглашений или auth-токенов. В нём есть условия, отдельные команды, исключённые случаи и агрегаты. `stage=complete` означает завершение сценария; соответствие целям проверяется отдельными полями summary. При недостаточной выборке облачный замер остаётся незавершённым. Превышение предварительных целей записывается как отклонение для задачи 4.4, без объявления целей достигнутыми.

При прерывании длинного прогона можно объединить несколько сессий с теми же условиями: `node scripts/summarize-cloud.mjs /tmp/summary.json report-1.json report-2.json`. Скрипт сохраняет все исходные отчёты, проверяет одинаковые условия и настоящий облачный backend, отдельно показывает число законченных сессий, все исключённые команды, авторство/revision и совпадение play/pause/rate через 3 секунды. Скрипт принимает собственный итоговый JSON для независимого пересчёта. Достаточная выборка для p95 не означает успешность длинного E2E-сценария.

## Границы

Разбор 4.4: сброс около команды 24 воспроизведён и в Chromium без расширения/Firebase. Контрольный запуск — `npm run probe:youtube-delivery`; данные и screenshot сохраняются в `.output/youtube-delivery/`. Он намеренно возвращает exit 1 при остановке доставки и не является успешным облачным замером. Настоящая ошибка плеера и восстановление адаптера отдельно проверяются `YOUTUBE_DELIVERY_REAL=1 npm run test:player`. Эти проверки не заменяют длинный облачный E2E. Выводы — в [журнале 4.4](youtube-sync-prototype.md#разбор-сброса-media--задача-44).

Повтор 2026-11-03 после исправления скорости: три облачных попытки (исходный ролик headless/с видимыми окнами и другой ролик headless) снова прерваны. Контроль без расширения повторил сброс и в установленном Google Chrome: `YOUTUBE_PROBE_CHANNEL=chrome YOUTUBE_PROBE_HEADLESS=0 npm run probe:youtube-delivery`. Допустимы каналы `chromium` (по умолчанию) и `chrome`; используется новый временный профиль, существующий профиль пользователя не затрагивается. Все эти запуски выполняются через Playwright. Результаты — в [журнале повтора](youtube-sync-prototype.md#повтор-длинной-облачной-приёмки--2026-11-03).

Последующая [проверка двух обычных профилей Chrome без Playwright](youtube-manual-acceptance-2026-11-03.md): 31 действие, позиция 5:54, прежний сброс не повторился. Обнаружено расхождение клавиатурной скорости при русской раскладке. Эта проверка интерфейса не измеряла точный p95, позиции через 3 с или число revision и не объединяется с инструментальной выборкой. Следует сначала разобрать различие обычного и автоматизированного запуска; другой сетевой маршрут не является обязательным условием продолжения. Сеть не менялась.

Два профиля на одном хосте разделяют компьютер и внешний сетевой маршрут. Такой прогон измеряет облачный RTDB и настоящий YouTube для указанного окружения; он не доказывает задержку между двумя странами или двумя независимыми сетями. Сетевые условия и регион backend должны быть записаны буквально; неизвестный VPN или тип доступа нельзя объявлять отсутствующим. Сетевой throttling не включается. Свежие профили не обходят рекламу; её наличие видно в отчёте.

Проверка самого стенда с эмуляторами и управляемым media:

```sh
npm run build:transport
WXT_FIREBASE_EMULATORS=1 node scripts/firebase.mjs emulators:exec --only auth,database,hosting --project demo-watch-together "npm exec -- playwright test --config playwright.cloud.config.ts"
```

Этот результат всегда помечается `rehearsal: true`, `liveYouTube: false`, и не может дать положительный результат облачной приёмки.

## Наблюдение в обычном Chrome

Эта методика не подключает Playwright/CDP к браузеру. Наблюдатели входят только в локальную QA-копию уже собранного расширения, используют DOM media и существующий read-only status API, не меняют разрешения и не отправляют playback-команды.

```sh
npm run build:cloud
node scripts/native-measurement.mjs
```

1. Загрузить или перезагрузить `.output/cloud/chrome-mv3` через `chrome://extensions` в двух независимых QA-профилях обычного Chrome. Открыть один ролик YouTube, создать комнату в A через action popup, войти в B по приглашению. В каждом профиле оставить только одну комнатную привязку.
2. В каждом профиле открыть `chrome-extension://EXTENSION_ID/popup.html` в отдельном окне; ID взять из карточки расширения. Оба status-окна и оба плеера должны оставаться видимыми. Фоновые вкладки могут замораживаться и не подтверждают полноту истории revision. Дождаться двух участников, соединения и одинаковой исходной revision до первого ввода.
3. На наблюдателе поверх YouTube нажать «A: начать» и «B: начать» соответственно. Вернуть фокус на плеер; setup-действия, меняющие playback, закончить до начала измерений. В итоговом прогоне фокус возвращался через правый клик по плееру и Escape, без новой команды.
4. Выполнять trusted клавиши вручную, чередуя профили сериями по восемь: Space, Shift+Period, ArrowRight, Space, ArrowLeft, Shift+Comma, Space, Space. Выдерживать более 3,1 с после каждого действия; в приёмке использовано ожидание 3,5 с плюс время UI. Набрать минимум 30 пригодных команд, включая оба направления управления. Дождаться окончания окна последней команды.
5. Скачать media A/B через «Скачать media» и оба status JSON через «Скачать QA status». Кнопки останавливают запись; повторный прогон требует нового старта media и reload status-документов. Порядок status при расчёте должен соответствовать media A/B.

```sh
node scripts/summarize-native.mjs /tmp/native-summary.json media-A.json media-B.json status-A.json status-B.json
# Независимый пересчёт сохранённой приёмки:
node scripts/summarize-native.mjs /tmp/native-summary.json --raw docs/experiments/youtube-native-48-2026-11-03.raw.json.gz
# Удалить наблюдателей из QA-сборки по окончании:
npm run build:cloud
```

После последней сборки перезагрузить расширение в обоих QA-профилях и обновить YouTube-вкладки, закрыть status-окна. Обычная сборка не содержит наблюдателей. Скрипт расчёта возвращает exit 1 при недостаточной выборке, неприменённой пригодной команде, превышении цели, неполной истории авторства/revision, лишней финальной revision, несовпадении play/pause/rate или ошибках status. Сохранять обе сырые пары, окружение, хеши сборки и исключённые команды; не объединять разные условия или неполные прогоны с успешной приёмкой.
