# ADR-0002: Firebase для комнат и анонимной идентификации

Дата: 2026-11-02  
Статус: принято для технического прототипа по результатам задач 1.3–4.4; ограничения публичного MVP перечислены ниже.

## Контекст

Нужны состояние комнаты, обновления для нескольких участников и автоматическая анонимная авторизация. Комната должна работать после ухода создателя. Для MVP предварительно выбран Firebase Realtime Database без собственного WebSocket-сервера.

## Решение

- Firebase RTDB хранит состояние комнаты и присутствие участников.
- Firebase Anonymous Auth даёт технический UID; имя и номер участника задаются в контексте комнаты.
- Клиент расширения использует поддерживаемый entry point firebase/auth/web-extension там, где SDK работает в extension context.
- Firebase Security Rules проверяют доступ к конкретной комнате и допустимость изменений. Сам по себе анонимный вход не даёт доступа ко всем комнатам.
- Приглашение содержит непредсказуемый идентификатор/секрет; список чужих комнат не доступен. Точная схема членства проверяется эмулятором.
- Firebase Hosting обслуживает простую HTTPS-страницу приглашения.
- Закрытие вкладки или выход создателя удаляет его присутствие, но не комнату.
- Клиент хранит опорную позицию, скорость, состояние и время; постоянная отправка позиции на каждый timeupdate не требуется.

## План проверки до принятия (история эксперимента)

Контекст выбран ниже; правила доступа и поведение комнат ещё проверяются. Нельзя считать popup постоянно открытым или предполагать бесконечную жизнь service worker.

Проверяем единый UID при нескольких вкладках, presence через onDisconnect, серверное время, конфликтующие записи, повторное подключение и отсутствие отложенных старых команд после offline.

Для эксперимента порядок действий задаётся версией состояния и транзакцией. Серверные timestamps и оценка смещения часов помогают вычислять позицию, но их точность измеряется.

## Выбор контекста — эксперимент 1.3

Для реализации room transport выбираем **extension-origin документ внутри вкладки просмотра**: локальный `session.html` в iframe. Документ владеет RTDB-подписками и живёт вместе с вкладкой; popup служит интерфейсом, service worker выполняет короткие browser-операции. Экспериментальный код находится в `experiments/firebase-context/`, результаты и условия — в [журнале](../experiments/youtube-sync-prototype.md#firebase-контекст-и-mv3--задача-13).

- Anonymous Auth использует `firebase/auth/web-extension` и явно заданный `indexedDBLocalPersistence`. Во всех контекстах совпадают origin, Firebase app name и apiKey. Первый вход, включая инициализацию и чтение persistence, выполняется под общим Web Lock; две вкладки и worker при одновременном первом старте получили один UID. Другой browser profile получил отдельный UID.
- RTDB запускается с `forceWebSockets()` до первой подписки. Обычный fallback на long polling пытался загрузить внешний JSONP script и нарушал MV3 CSP, в том числе после reload. WebSocket-only прошёл матрицу со строгим `script-src 'self'`; если WebSocket недоступен, клиент должен показывать отсутствие связи, а не ослаблять CSP.
- Закрытие настоящего action popup и принудительная остановка worker не прервали получение обновлений двумя iframe. Reload документа сохранил UID и получил свежие данные; закрытие одной вкладки не прервало другую.
- Восстанавливаемый worker тоже поддерживает Auth/RTDB и читает свежие данные после явного пробуждения. Но при остановленном worker и отсутствии документов нет исполняемой подписки; нужен отдельный источник пробуждения. Поэтому его не выбираем владельцем подключения во время просмотра.
- Владение сессией должно быть явным: один документ на связанную вкладку комнаты; при выходе снимаются подписки и закрывается соединение, при reload читается актуальная версия. Presence через `onDisconnect` и восстановление room session относятся к следующим задачам, эксперимент их ещё не реализует.
- В iframe загружается только bundled extension-код. Auth и UID не отправляются через `window.postMessage` и не помещаются в URL/DOM страницы. Будущий bridge с изолированным content script должен проверять отправителя и структуру сообщений; полномочия и секреты нельзя доверять коду сайта. Эксперимент проверяет контексты без продуктового bridge.

Chrome документирует общий storage для extension-origin контекстов и исключение встроенных extension-страниц из storage partitioning. Проверка выполнена на bundled Chromium 156 с локальной Hosting-страницей, а не на YouTube; ограничения внедрения iframe на настоящем сайте ещё проверяются. Полное принятие backend ADR остаётся за проверками Rules, presence, конфликтов, offline и выхода создателя.

## Реализация контекста — задача 2.1

Auth и transport чтения перенесены в основной `src/`: popup и session-документ используют общий Firebase app name и Web Lock, iframe владеет подписками соединения, серверного времени и выбранной комнаты. Popup обращается к session через внутренние сообщения с проверкой sender ID, точного URL `popup.html` и Zod-схемы. Content script только создаёт iframe и возвращает его публичный адрес; UID, секрет и данные через него не передаются. При закрытии документа подписки снимаются, SDK переводится offline и удаляется без signOut: сохранённый UID остаётся доступен другим вкладкам.

Browser-матрица использует основной код с локальными эмуляторами; отдельно подтверждена загрузка iframe и Anonymous Auth на настоящем YouTube. Обычный manifest содержит YouTube host permissions и доступный этому сайту `session.html`; localhost разрешён только в сборке с `WXT_FIREBASE_EMULATORS=1`. Облачная конфигурация ещё не подключена. Rules, presence, конфликты и offline-команды по-прежнему требуют проверки до принятия ADR целиком.

## Проверка доступа — задача 2.2

Локальные RTDB Rules и интеграционная матрица подтвердили доступ по полному секретному ключу комнаты после Anonymous Auth, запрет перечисления и изменения чужого presence. Отдельного membership нет: передача полного ключа приглашает любого авторизованного клиента. Другой случайный ключ не открывает исходную комнату; отсутствующая комната возвращает `null`. Правила проверяют структуру playback, автора, серверное время, последовательную revision и неизменность исходного видео. Запись комнаты целиком после создания закрыта, поэтому через неё нельзя удалить или подменить чужой presence. Контракт и форматы данных — в [design](../../openspec/changes/archive/2026-11-03-youtube-sync-prototype/design.md#контракт-rtdb-rules--задача-22), результаты — в [журнале](../experiments/youtube-sync-prototype.md#правила-доступа-rtdb--задача-22).

Проверки выполняются под настоящими Anonymous ID tokens без admin-доступа и замены Rules. Они подтверждают серверные ограничения, но не реализацию presence lifecycle, транзакций, idempotency и offline в расширении. Эти проверки, облачные измерения и окончательное принятие ADR остаются впереди.

## Восстановление — задача 3.5

Синхронизация после reconnect ждёт свежего чтения комнаты. Основной SDK-клиент сохраняет cache активной подписки, поэтому разовый read выполняет отдельный временный Firebase app: Auth в памяти получает копию текущего Anonymous User, пустой RTDB cache вынуждает `get` обратиться к серверу. Клиент не пишет presence, не создаёт UID и удаляется после чтения/отмены. Всё выполняется в том же extension-документе через WebSocket; ключ и Auth не добавляются в HTTP URL.

Поколение соединения и AbortSignal отсекают действия предыдущего соединения; engine не ждёт старый ack после восстановления. Более новая revision основной подписки сохраняется, presence не заменяется запоздавшим снимком. При ошибке свежего чтения общие команды остаются заблокированными, доступен повтор подключения. Сетевые проверки двух profiles покрывают offline до записи, потерю пакета транзакции и потерю ack принятой записи, с командами другого участника и без них. Условия и результаты — в [журнале](../experiments/youtube-sync-prototype.md#offlinereconnect--задача-35). Облачные измерения и окончательное принятие ADR остаются задачами 4.3–4.4.

## Альтернативы

Собственный WebSocket-сервис даёт больше контроля над порядком команд, но требует эксплуатации сервера. Firestore допустим как другое облачное хранилище, однако RTDB уже предварительно выбран и предоставляет presence. P2P потребует дополнительных решений для подключения и восстановления комнаты.

## Последствия

Видео продолжает загружаться с YouTube. Авторизация и правила доступа проверяются независимо от UI. Удаление пустых комнат, срок приглашений и эксплуатационные лимиты решаются до публичного MVP.

Условия принятия для технического прототипа выполнены: Auth/UID, Rules, presence, транзакции/конфликты, offline/reconnect, закрытие popup, остановка worker, reload и выход создателя проверены в локальной и реальной YouTube-матрице. Облачные измерения 4.3 подтверждают пригодность RTDB в проверенном окружении (два профиля на одном Mac и маршруте); они не доказывают задержки между независимыми сетями. Повторная проверка 4.4: 38 integration-тестов и 27 transport-сценариев успешны.

Сброс media воспроизведён и в Chromium без расширения/Firebase. Это не основание менять backend: доставку видео RTDB не обслуживает. Причина сбоя YouTube/среды не установлена, полная приёмка плеера остаётся открытой. Исходные результаты — в [разборе 4.4](../experiments/youtube-sync-prototype.md#разбор-сброса-media--задача-44).
