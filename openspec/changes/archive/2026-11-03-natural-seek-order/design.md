# Design

## Context

См. proposal.md. Сейчас адаптер использует debounce 120 мс, не отслеживает keyup и при remote apply очищает жест. Engine отбрасывает ввод во время записи, транзакция требует равенства baseRevision. RTDB offset уже доступен extension session; revisions по-прежнему нужны для порядка snapshot и серверной записи.

## Goals / Non-Goals

**Goals:** удержание и серия нажатий дают конечную позицию; пользователь заканчивает жест без вмешательства удалённого состояния; более позднее действие побеждает при перестановке доставки.

**Non-Goals:** новый backend, offline-очередь, идеальный физический порядок при неточных часах, изменение личных настроек плеера или границ MVP.

## Decisions

1. PlayerIntent содержит `actionAt` (клиентский timestamp завершения ввода) и `sampledAt` (время считывания позиции). Session переводит оба в серверные часы через `.info/serverTimeOffset` один раз до ожидания записи. Timestamp не зависит от timezone. Для последовательных действий одного клиента время монотонно; одинаковые отметки разных участников оставляют первую принятую команду. Альтернатива — порядок доставки — противоречит согласованному поведению.
2. Playback хранит эти две метки, `updatedAt` остаётся серверным временем принятия записи. Позиция рассчитывается от `sampledAt`. Обе метки обязательны во всех версиях playback. При создании комнаты все три метки задаются через serverTimestamp; обратная совместимость не поддерживается.
3. Транзакция сравнивает `actionAt` с принятым действием; допускает старую baseRevision, отклоняет будущую. При записи revision берётся из текущего серверного состояния + 1. Повтор сверяется по id/автору/payload/меткам, без предположения revision = baseRevision + 1. Callback не меняет метки или id. Rules обеспечивают рост revision и actionAt, проверяют обязательность и числовые границы меток и не допускают метки дальше 5 с в будущем; клиентская оценка времени не является доверенными серверными часами.
4. Адаптер отслеживает pointer и нажатые seek-клавиши. Пока они удерживаются, debounce не отправляет данные. После отпускания таймер ждёт 120 мс и окончания `video.seeking`; итоговая позиция считывается при отправке. Повторные keydown продолжают тот же жест, включая локальное buffering. Отмена по blur/pointercancel, смене media, рекламе и навигации снимает защиту.
5. Отдельное внутреннее player interaction event сообщает engine о незавершённом жесте. Engine откладывает apply; адаптер дополнительно отклоняет apply при активном жесте для защиты от гонки сообщений. Intent завершает interaction атомарно, без промежуточного apply. Отмена восстанавливает последнюю комнатную версию.
6. Engine хранит одну неизменяемую следующую команду вместо очереди: новое действие заменяет её. Подтверждение старой команды не откатывает локальный плеер. Следующая отправляется только после освобождения транспортного пути и при актуальности относительно последнего `actionAt`. Disconnect/выход/локальное ограничение отменяют её; buffering собственной перемотки разрешён. Apply приостанавливается, пока локальное действие более новое; более позднее удалённое состояние применяется после завершения жеста.

## Risks / Trade-offs

- Погрешность серверного offset → действия в пределах этой погрешности могут быть упорядочены иначе; абсолютная гарантия физического порядка невозможна. На одном клиенте сохраняем монотонность, не используем timezone и время доставки.
- Долгое удержание → остальные видят перемотку после отпускания, как согласовано пользователем.
- Медленная media-загрузка → ждём подтверждения позиции; локальные ограничения и отмена не создают общих команд.
- Настоящий YouTube может иначе формировать события → browser fixture проверяет механику, результат live-проверки записываем отдельно и не выдаём fixture за live.
- Новый протокол несовместим с прежним форматом playback → по решению пользователя обратная совместимость и миграция не нужны: расширение ещё никто не использует.

## Migration Plan

После локальных проверок развернуть только Database Rules в настроенном QA-проекте через `npm run deploy:rules` и сверить активные Rules с локальным контрактом. Сборка расширения устанавливается отдельно. После выполнения задач синхронизировать основные specs и архивировать change. Откат требует совместного возврата Rules и сборки с созданием новой комнаты.
