# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md); поведение — в delta specs `shared-playback` и `room-session`.

Наблюдения по коду:

- `preparePlaybackCommand` и RTDB Rules запрещают изменение `videoId`. Состояние хранит монотонную `revision`, `actionAt`, `sampledAt`, `commandId`; порядок обычных действий уже определяется временем действия в серверных часах.
- `session.html` владеет transport и engine, content script — адаптером плеера. Адаптер выдаёт `different-video`; session показывает ссылку возврата. Snapshot текущего ролика сейчас разрешён только popup.
- `engine.applyLatest` ждёт `ready`. Поэтому просто разрешить новый `videoId` недостаточно: старый адаптер останется в `different-video`, а навигация не начнётся. Обработка смены должна предшествовать проверке готовности старого плеера.
- `background.ts` сериализует операции с `storage.session`, проверяет session target и восстанавливает связь вкладки с ключом. `focus` умеет активировать вкладку без навигации; открытие уже существующей из каталога использует этот путь.
- Каталог содержит `videoId` как сохранённый snapshot. При отсутствии связанной вкладки `Catalog.tsx` читает комнату с сервера, при наличии только активирует её. Автообновление через `saveRoom` вернуло бы удалённую запись — использовать этот путь при смене нельзя.
- Контекст в `config.yaml` частично описывает первоначальный прототип; актуальное состояние подтверждено README, основными specs и архивированными changes. Обратная совместимость не нужна по `docs/development.md`.

## Goals / Non-Goals

**Goals:** единая атомарная запись playback для смены ролика; защита старых команд при A → B → A; явное различение следования за комнатой и локального ухода; безопасное восстановление после смены документа и потери ack.

**Non-Goals:** зависимость от внутренних API навигации YouTube, отдельный backend, перенос Auth/секретов в content script, непрерывное воспроизведение без загрузки страницы. Полная навигация связанной вкладки допустима.

## Decisions

### 1. Два типа команды и поколение общего просмотра

Расширить обязательный playback полями `kind: 'playback' | 'switch-video'` и `videoRevision` — номером revision, на которой начался текущий просмотр. При создании оба счётчика равны 0, `kind = 'playback'`. После обычной команды `videoRevision` сохраняется, после принятой смены равен новой `revision`. После любого следующего переключения, даже назад на A, поколение другое.

Входящие команды — строгий discriminated union:

- `playback`: прежний snapshot и timing, `baseRevision`, `commandId`, обязательный `videoRevision`. Допускается только для текущих `videoId` и `videoRevision`.
- `switch-video`: целевой snapshot и timing, `baseRevision`, `commandId`. Выражает самостоятельное намерение сменить видео и не зависит от исходного поколения. На транзакционном актуальном состоянии назначается новое поколение. Если целевой ролик уже общий, команда завершается без изменения.

Общие ограничения сохраняются: `baseRevision` не из будущего, `actionAt` строго новее принятого, revision повышается на 1, server timestamp пишет сервер. Две явные смены согласуются по `actionAt`, даже если поступили в обратном порядке; при равенстве сохраняется первая принятая. Обычная команда прежнего поколения недопустима независимо от `actionAt` — это явное уточнение прежнего требования о конфликтах, отражённое в delta.

`preparePlaybackCommand`, отправка transport и duplicate-проверка охватывают оба типа, kind и поколение. Сохраняется существующая дедупликация текущей принятой команды; повтор более старой команды отклоняется без записи. Не добавляем историю команд.

Альтернатива — только снять проверку совпадения `videoId` — не различает пользовательскую смену и старый seek. Проверка только `videoId` также не защищает A → B → A. Сброс `revision` при смене неприемлем: ломает порядок подписок и reconnect.

### 2. Серверная проверка переходов

RTDB Rules проверяют обязательность kind/поколения, целочисленные границы и `0 <= videoRevision <= revision`:

- создание: `revision = videoRevision = 0`, `kind = 'playback'`;
- обычное управление: неизменные `videoId` и `videoRevision`, `kind = 'playback'`;
- смена: отличный `videoId`, `kind = 'switch-video'`, `videoRevision = revision` новой записи.

Авторство, `updatedAt === now`, увеличение revision, порядок timing, запрет личных/лишних полей и ограничения metadata/presence сохраняются. Свойство «нажата кнопка» обеспечивается trusted UI и сообщениями расширения: Rules валидируют структуру и переход, а не физическое действие человека.

### 3. Действие в существующем session-индикаторе

Кнопка «Смотреть это в комнате» находится в extension iframe связанной вкладки, рядом с возвратом. Popup не получает второй независимый механизм смены. Кнопка доступна для отличного поддерживаемого videoId при готовой комнате и связи; ошибки плеера проверяются повторно при выполнении. Высота/прокрутка индикатора учитывает дополнительные элементы, чтобы возврат и выход оставались доступны.

При trusted click session фиксирует `actionAt`, получает свежий snapshot через разрешённый session-target путь к content script и фиксирует `sampledAt` при чтении media. Snapshot включает идентификатор версии локальной навигации; перед отправкой проверяются target, ролик, версия навигации и готовность комнаты. Между запросом и проверкой сменился документ/ролик — отменить действие и предложить повтор. Название нового видео не передаётся в metadata комнаты.

Snapshot повторно использует проверку готовности из пути создания: обычное конечное видео, без рекламы и активного seek. Простое чтение не подключает второй публикующий адаптер. Схемы и sender checks расширяются точечно: session из назначенного iframe может читать только свою связанную вкладку; content script не выбирает комнату и не получает секрет, UID или Auth.

Пока ожидается ack, кнопка заблокирована. Автоматического retry с новым временем нет; явный повтор получает новый snapshot и id. После commit/подтверждённого duplicate инициатор переходит в следование; при отказе сохраняет локальный просмотр. До отправки в привязке сохраняется pending-switch: commandId и целевой videoId, без очереди для повторной отправки. Если ack потерян, reconnect читает фактический серверный результат; совпадающие commandId/авторство позволяют распознать собственную принятую смену без повторной записи, в том числе после reload. Если после неё уже принято другое действие и подтверждения собственной смены нет, успех не выводится из одного совпадения videoId: показывается актуальное состояние и предлагается явный возврат. Подтверждение старой операции после выхода или нового target игнорируется; pending-switch очищается после разрешения результата или выхода.

Альтернатива — сразу считать локальную навигацию общей — противоречит P-08. Получение snapshot только через popup потребовало бы держать popup открытым и не даёт действия в самой вкладке.

### 4. Явное состояние следования и навигация через worker

В привязке вкладки `storage.session` хранить режим `following | detached`, подтверждённое поколение и последнюю принятую цель навигации с revision/operation token. Начальные create/join/открытие закрытой комнаты включают `following`. Обычный уход на другой ролик включает `detached`, сохраняющийся при reload и остановке worker. Совпадение локального videoId с новой серверной целью само по себе не включает синхронизацию; собственная навигация на текущее общее видео или явный возврат включает её.

Навигация комнаты проходит через отдельное сообщение из проверенного session iframe в сериализованный worker, без `saveRoom` и catalog upsert. Worker проверяет target и актуальность операции, сохраняет pending-цель до `tabs.update`, затем переводит ту же вкладку на канонический `https://www.youtube.com/watch?v=…`. Секрет в URL не попадает. Полная навигация использует проверенный путь восстановления Auth/transport; transient presence при смене документа допустим, устойчивых двойных соединений быть не должно.

Content script сообщает изменения маршрута вместе с локальной последовательностью навигации. Ожидаемый переход с соответствующим token — переход комнаты; самостоятельный переход, не совпадающий с ожидаемым, отменяет устаревшую навигационную операцию и включает `detached`. Отложенный запрос worker не должен перетирать более свежую локальную навигацию: перед `tabs.update` повторно сверяются target, локальная последовательность и последняя цель. Pending-цель потребляется после восстановления нужного документа. Не переименовывать immutable metadata и не использовать смену как повод сохранить каталог.

После восстановления session сначала получает актуальное состояние сервера, затем выбирает цель. В режиме `following` несовпадение текущего videoId с последней целью вызывает переход до ожидания `ready`; в режиме `detached` обновляется только действие возврата. «Вернуться в комнату» проходит тот же trusted путь, предварительно получает актуальное состояние и включает `following`; перестаёт быть простой ссылкой на потенциально устаревший snapshot. Активация живой вкладки из списка сохраняет её режим. Повторное приглашение использует существующий явный путь входа в актуальное видео.

Альтернатива — считать любой `different-video` локальным уходом — остановит и входящие смены. Всегда возвращать на серверный videoId при reload разрушит локальный просмотр. Прямое обращение к недокументированному SPA API YouTube не требуется; полная загрузка проще для первой реализации.

### 5. Границы engine и адаптера

Новая `videoRevision` отменяет старые apply, готовность, активный жест и queued обычную команду прежнего поколения. Callback старого адаптера маркируется поколением и локальным adapter token; события без совпадения игнорируются до создания нового адаптера. Не переиспользовать событие старого video A для нового просмотра A.

Смена обрабатывается session/координатором до блокировки `applyLatest` по готовности: инициатор уже открыл целевой ролик и создаёт актуальный адаптер; following-получатель сначала переходит на цель, затем читает последнее playback и применяет рассчитанную по `sampledAt` позицию. Проверка commandId собственного действия не должна пропустить переустановку адаптера и поколения.

Все общие отправки проходят один шлюз in-flight в transport. Смена не ставится в очередь обычных действий; пока она отправляется, новые смены недоступны. Disconnect/выход отменяют неотправленные запросы, старые ответы не управляют новым session. Новое состояние во время загрузки заменяет цель; старые результаты не запускают откат или цикл reload. При autoplay, недоступности или buffering используются существующие локальные состояния без общей команды.

Альтернатива — управлять навигацией из `adapter.apply` — смешивает различение локального ухода с media-применением и может запускать переход в ответ на старый callback. Engine остаётся без browser/Firebase API.

## Risks / Trade-offs

- [Гонки маршрута и смена документа] → persisted token и режим, повторная сверка перед навигацией, tests с задержанными ответами и быстрыми сменами. Гипотеза: существующего восстановления session достаточно для полной навигации; подтвердить в двух профилях и обычном Chrome. При сбоях пересмотреть координатор, не ослаблять no-echo и локальность перехода.
- [Media-ошибки автоматизированного YouTube уже воспроизводились без расширения] → отдельно фиксировать инфраструктурную ошибку, сохранять неудачные попытки; стенд не заменяет live-приёмку. Недоступные live-сценарии остаются открытыми.
- [Полная загрузка увеличивает время до готовности и может потребовать play] → показать переход/локальное ограничение, применить последнюю revision. Прежний SLA 1 с относится к командам при готовых плеерах, не к загрузке нового ролика.
- [Часы близких действий неточны] → сохраняется текущий Firebase offset и правило равных меток; поколение защищает старые обычные команды независимо от этой погрешности.
- [Обновление состояния привязки может вернуть удалённый каталог] → отдельный путь без upsert, регрессионный browser-тест удаления перед сменой/reload/worker restart.
- [Прежние fixtures и QA-комнаты несовместимы] → обязательные поля, проверка отказа старого формата; не добавлять fallback ради прохождения прежних тестов.

## Migration Plan

1. Реализовать модель, Rules и границы сообщений; обновить fixtures только на новый контракт. Сохранить запрет доступа content scripts к local storage и Auth.
2. Проверить unit/integration/browser-матрицы на эмуляторах, сборку и specs. README и PRD уточняются после реализации с разделением готового поведения и ограничений.
3. Перед live QA обновить только Database Rules тестового проекта, сверить активную версию и собрать актуальную cloud-сборку. Оба профиля используют одинаковую сборку и новые комнаты. Схема локального каталога не меняется; старые серверные комнаты отклоняются без миграции.
4. Выполнить live-приёмку и сохранить обезличенный отчёт. Не архивировать change до выполнения задач приёмки.
5. При откате вернуть согласованную пару прежней сборки и Rules, использовать комнаты соответствующего формата; данные нового формата не преобразовывать. Проверки и публикация относятся к apply, этот документ ничего не развёртывает.
