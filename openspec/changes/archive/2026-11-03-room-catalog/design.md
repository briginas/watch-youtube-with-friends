# Design

## Context

Мотивация и продуктовые границы — в [proposal.md](proposal.md). `background.ts` уже последовательно обрабатывает открытие, привязку и закрытие вкладок, хранит `roomTabBindings` в `storage.session`. Проверка отправителей требует `sender.tab.id`; обычный popup этому условию не соответствует. Firebase работает в `session.html` и `invitation.html`, popup получает общий Anonymous UID, но не держит RTDB-подписки. Приглашение проверяет комнату без presence, затем worker открывает watch-вкладку.

Постоянного списка и названий нет. `invitationRoomSchema` читает playback; Rules запрещают все поля комнаты, кроме playback/presence. `watch-session.content.ts` получает snapshot плеера, но не название видео. Тесты создания явно проверяют набор полей комнаты, а `tabs.spec.ts` уже проверяет повторное приглашение и отсутствие повторного подключения.

В config OpenSpec остался контекст подготовки прототипа; актуальные README, PRD и архивы подтверждают его завершение. Этот change продолжает MVP после прототипа.

## Goals / Non-Goals

**Goals:** разделить постоянные записи и временные подключения, сохранить одного владельца изменений списка/вкладок, использовать существующие transport и sync engine. Добавить обязательную metadata без изменения playback revision. По решению пользователя поддерживать только актуальный формат, без миграций и совместимости с прежними версиями.

**Non-Goals:** Firebase в worker, серверный индекс комнат или presence для списка. Остальные продуктовые исключения перечислены в proposal.

## Decisions

### 1. Локальный repository, отдельный от привязок вкладок

Добавить `src/lib/room/catalog.ts` с Zod-схемой версии хранилища и чистыми операциями чтения/обновления записей. Хранить список в `browser.storage.local`, ограничив доступ trusted extension contexts через `setAccessLevel`. Устанавливать ограничение до первого чтения/записи каталога; при ошибке не сохранять секреты в доступное content scripts хранилище. `storage.sync` не используется: список относится к одному профилю.

Namespace окружения включает нормализованные projectId, databaseURL и invitationBaseUrl; localhost/emulator и cloud не смешиваются даже при обновлении одной установки. При отсутствии конфигурации popup показывает сообщение о ненастроенном сервере и не открывает чужие namespace.

Запись содержит `key`, `videoId`, `name`, `savedAt`, `lastOpenedAt`. Идентичность — namespace плюс полный ключ, а не videoId или название. Сортировка — последнее явное открытие/создание сверху; равенство разрешается стабильным порядком ключей. Сырые ключи не показываются как подпись. Невалидные записи пропускаются отдельно с сообщением; неизвестная версия каталога не перезаписывается автоматически. Ошибка записи сообщается отдельно от результата входа.

Новые привязки используют отдельный ключ `roomTabBindingsV2` в `storage.session`; данные прежнего ключа не читаются и не мигрируются.

Все изменения выполняет worker через расширенную существующую очередь: upsert и remove разных вкладок не теряют чужие записи. Фоновая подписка комнаты не выполняет upsert: удалённая запись не возвращается после onValue, reload или остановки worker. Изменение storage уведомляет открытый popup.

Альтернативы: `storage.session` теряет список после перезапуска; серверный список требует новой модели пользовательских данных и правил; прямая запись из каждого документа создаёт гонки read-modify-write.

### 2. Только явные успешные операции сохраняют запись

Создание: после подтверждённого `set` transport возвращает данные новой комнаты, session запрашивает у worker привязку и сохранение записи. Принятие приглашения: после успешного серверного чтения и открытия/активации watch-вкладки worker сохраняет запись. Обновление существующей записи не меняет исходное имя.

Для нового входа `invitation.html` должен дождаться `roomReady`, а не принимать optimistic/onValue snapshot за актуальное серверное состояние. Секрет и metadata передаются только внутренними messages проверенного extension iframe. Открытие страницы приглашения не сохраняет комнату. Ошибка доступа или открытия вкладки не добавляет новую запись.

Ошибка storage после успешного подключения не откатывает просмотр: UI сообщает «Комната открыта, но не сохранена» и предлагает повторить сохранение в живом session-документе, даже если popup уже закрылся. Удаление отражается в UI только после успешной записи. Последовательность очереди определяет результат конкурирующих явных операций; запоздавшие callback завершённой операции не создают новый upsert.

Существующие привязки вкладок не импортируются фоновым сканированием. Комнату актуального формата можно добавить явным повторным принятием приглашения; привязки и комнаты предыдущих версий не мигрируются.

### 3. Открытие из popup через тот же механизм вкладок

Выделить в worker общий сериализованный путь открытия, вызываемый приглашением и новым запросом из точного extension popup URL. Обработку popup выполнять до обязательной проверки `sender.tab.id`; для session/invitation сохранить проверки origin, frameId и target. Popup-запрос открывает только запись текущего namespace, существующую в repository.

Сначала worker ищет живую связанную вкладку и активирует её с фокусом окна; для этого не нужна новая подписка и проверка сети. Если вкладки нет, popup как extension-документ выполняет ограниченное по времени серверное чтение существующим `readRoom` с общим UID, проверяет модель и передаёт актуальное videoId в worker. Worker повторно проверяет запись и привязки внутри очереди, чтобы приглашение и popup не создали две вкладки. После этого используется существующая схема about:blank → сохранение binding → watch URL; session читает актуальное состояние перед sync.

Временный reader освобождается при закрытии popup, его результат после отмены игнорируется. При закрытии popup уже переданная worker операция открытия завершается независимо. Ошибки до открытия новой вкладки отображаются у записи, после передачи владения — в session. Отсутствующая комната, отказ и сеть не удаляют сохранённую запись. Недоступность видео в YouTube остаётся локальной ошибкой плеера по действующим правилам.

Альтернатива открытия hosting-приглашения из списка добавляет лишнюю страницу и второе нажатие. Firebase в worker нарушает выбранную MV3-архитектуру и не требуется.

### 4. Обязательная неизменяемая metadata

При создании клиент добавляет обязательную `metadata: { name }` в тот же подтверждаемый write, что и playback. Rules и парсер комнаты требуют metadata с непустой строкой `name` длиной до 200 символов и запрещают посторонние поля. Запись/изменение/удаление metadata после создания запрещены. Общие команды продолжают изменять только playback. Комнаты без metadata имеют неподдерживаемый формат: показывать ошибку, не запускать sync/presence и не добавлять запись; не дописывать им поля автоматически.

`watch-session.content.ts` в ответ на доверенный popup snapshot возвращает отдельно нормализованное название текущего видео: предпочесть video title из watch DOM, убрать лишние пробелы и ограничить длину. Проверить соответствие snapshot текущему videoId при SPA-переходах. Если подходящее название не готово, использовать `Видео <videoId>`, без дополнительного сетевого API. Обновить create messages, transport и парсер комнаты. Fallback применяется при создании новой комнаты, а не при чтении старого формата.

Название отображается текстом через React/textContent, не через HTML. Общая metadata нужна гостям без собственной загрузки названия; хранение только у создателя давало бы разные подписи. Ручное переименование не вводится.

### 5. Popup разделяет каталог и текущую вкладку

Каталог загружается независимо от проверки активной страницы и готовности Firebase текущей watch-сессии. Секция списка имеет пустое состояние, имя, «Открыть» и «Убрать из списка», состояние операции и ошибку записи. Управление существующей комнатой текущей вкладки сохраняется отдельно. Список не показывает недостоверные online/presence или позицию из локального cache.

Удаление из списка не вызывает unwatch/release и не закрывает вкладку. Выход из комнаты, наоборот, снимает binding/presence существующим путём и сохраняет каталог. Перезапуск браузера сам по себе не обходит это разделение: расширение не восстанавливает просмотр по `storage.local`.

### 6. Жизненный цикл без TTL

Решение пользователя от 2026-11-03: пустые комнаты и приглашения действуют без автоматического истечения, удалить можно локальную запись. В текущей схеме это не требует scheduler или серверного удаления. Отразить решение в PRD Q-04 при реализации. Эксплуатационную очистку можно вводить отдельным change с согласованным поведением приглашений.

## Risks / Trade-offs

- [DOM YouTube и SPA могут дать прежнее название] → сверять videoId, брать название текущего watch-контекста, при сомнении использовать fallback. Это гипотеза адаптера до live-проверки; если достоверная проверка невозможна, сохранять fallback.
- [Длительное хранение ключей] → trusted storage, строгие sender checks и namespace, отсутствие секретов в DOM/URL YouTube, trace и логах. Локальное удаление не отзывает приглашение.
- [Неограниченное число записей и пустых комнат] → явное удаление записей и понятная ошибка квоты. Серверная очистка остаётся отдельным эксплуатационным решением; этот change не подтверждает готовность публичного сервиса.
- [Worker остановился между серверной записью и локальным сохранением] → не показывать ложного подтверждения каталога; повторное явное принятие приглашения идемпотентно. Не обещать атомарность RTDB и browser.storage.
- [Popup закрывается при фокусе другой вкладки] → чтение до передачи операции, владение открытием и записью у worker, сообщения об ошибке сохранения доступны в session.
- [Новая схема нарушит старые fixtures] → обновить fixtures и точные assertions под обязательную metadata, отдельно проверить отказ для прежнего формата; не ослаблять проверки playback.

## Rollout Plan

1. Реализовать и проверить локально под обновлёнными продуктовыми Rules; сохранить строгие ограничения playback/presence и запрет серверного перечисления.
2. В QA сначала опубликовать Rules актуального формата и сверить активную версию, затем собрать новую cloud-сборку. Все участники приёмки используют новую сборку и вновь созданные комнаты.
3. При первом запуске создать пустой namespace каталога. Миграций старых комнат, сообщений и локальных данных нет. Отсутствие TTL относится к комнатам актуального формата и не является обещанием межверсионной совместимости. Существующие QA-данные не удалять автоматически.
4. Проверить настоящий YouTube в двух обычных Chrome profiles: имя, повторный вход, независимые комнаты и удаление без остановки просмотра. Сохранить наблюдения и ограничения; стенд не заменяет live.
5. Откат версии, если потребуется, выполняется согласованным набором клиента и Rules с новыми QA-комнатами для выбранного формата. Сохранение работоспособности данных и приглашений между версиями не гарантируется; совместимость ради отката не реализуется.
