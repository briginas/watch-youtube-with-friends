> Публичная копия: сведения оператора обезличены; example IDs и контакты не являются действующей конфигурацией. Исторические результаты не подтверждают текущее состояние сервера.

# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md). План подготовлен на состоянии репозитория с `package.json` 0.2.0, HEAD `f2a2d81ec034d99fab89a4fb112b9773c2f717de`; это исходная точка исследования, не обещание будущего commit реализации.

Наблюдения по коду:

- `src/lib/firebase/settings.ts` задаёт один backend и один origin приглашений; `config.ts` фиксирует их в сборке. `scripts/release/config.mjs` требует, чтобы Hosting и RTDB принадлежали одному production-проекту.
- `wxt.config.ts` и invitation bridge разрешают только этот origin. `invitationKey()` принимает ровно `#room=<secret>` и проверяет точный origin/path.
- `roomMetadataSchema` strict и содержит только `name`; RTDB Rules запрещают дополнительные поля metadata. Новые поля нельзя безболезненно добавить в текущий production.
- Каталог ограничен профилем/конфигурацией, но записи и `roomTabBindingsV2` не содержат поколения. Поиск существующей вкладки сравнивает только ключ.
- Статус читается с `/service-status.json` на origin приглашений; retry/cancel и общий срок 15 секунд уже реализованы. Свежее чтение комнаты — REST с тем же Auth, без второго realtime-клиента.
- `scripts/release.mjs deploy` сейчас публикует Auth/Rules/Hosting одного выбранного проекта. Rules генерируются из текущего дерева, поэтому запуск нового кода со старой конфигурацией потенциально перезапишет прежний контракт.

Существующий production по runbook: `example-legacy-backend`; QA: `example-qa`. Live-инвентаризация облака в этом планировании не проводилась. `handle-service-capacity` завершён и архивирован; `prepare-public-release` остаётся отдельным change с незавершёнными публикацией и установкой из Store.

## Goals / Non-Goals

**Goals:**

- Сделать неизменяемое соответствие поколения одному backend и явно проверять его перед сборкой/deploy.
- Отделить долгоживущие адреса приглашений/реестра от удаляемых баз.
- Обеспечить понятный отказ от несовместимой комнаты и проверяемую ротацию с продолжением после ошибки.
- Проверить границы проектов и сбои локально без удаления настоящего production.

**Non-Goals:**

- Поддержка прежних схем комнат, миграции, автоматическое копирование комнат, выбор пользователем старого backend или загрузка старого кода.
- Принудительная установка/откат версии Chrome-расширения и сохранение комнаты после обновления на несовместимое поколение.
- Автоматическое определение совместимости по SemVer либо доказательство совместимости всех исторических клиентов.
- Обновление существующего production новым контрактом, включение billing, реальное provisioning/удаление проектов и публикация в Store в ходе локальной реализации.

## Decisions

### 1. Три backend-проекта плюс постоянный служебный проект

Пользователь отдельно подтвердил служебный Firebase-проект сверх лимита трёх backend-проектов. На нём только Hosting: страница приглашения, privacy, реестр и статусы. Auth, RTDB и секреты комнат остаются в проектах поколений. QA не зависит от production и может менять контракт без сохранения истории.

Служебный project ID и HTTPS origin выбираются при отдельном rollout; для кода и локальных проверок используются явные параметры и fixtures. Не привязывать их к удаляемому текущему production и не придумывать существующие ресурсы. QA использует собственный Hosting и тестовый реестр, а не production control origin. Внутри QA допустим один тестовый проект для Hosting и RTDB; отдельный постоянный служебный проект требуется именно для production.

Альтернативы: отдельный prod на каждый patch создаёт лишние проекты; общий изменяемый backend требует обратной совместимости; Hosting в старейшем backend исчезает при его ротации. Эти варианты не соответствуют выбранной модели.

### 2. Поколение отделено от версии расширения

Три независимых понятия:

| Поле | Значение | Изменяемость |
| --- | --- | --- |
| `releaseVersion` | Версия пакета из package.json, например 0.3.1 | Новое значение на релиз |
| `backendGeneration` | Непереиспользуемый идентификатор, например g0002 | Постоянен для контракта/project ID |
| `createdWithVersion` | Версия расширения, создавшего комнату | Неизменяем в metadata |

Идентификатор поколения — ограниченный slug `[a-z][a-z0-9-]{0,31}`; он не кодирует URL и не является секретом. Номер g0002 в примерах не означает автоматически созданный проект. Production-инвентарь запрещает QA/control поколения в backend-релизе.

Оператор явно выбирает `reuse` либо `new` и указывает предшествующий релиз. `reuse` означает прежний серверный контракт и тот же backend: более новый номер расширения сам по себе не отклоняет старую комнату. При несовместимости выделяется новый project ID. Проверка описания релиза и зафиксированных артефактов предотвращает случайную замену контракта; она не объявляется автоматическим доказательством семантической совместимости.

### 3. Локальный инвентарь и публичный реестр имеют разные задачи

Предлагаемые новые артефакты реализации:

- `.local/deployment/generations/inventory.json`: роли проектов, generation → project ID, `firstRelease`, состояние проекта, связь с release descriptors. Секретов и Auth-токенов нет.
- `.local/deployment/generations/releases/<version>.json`: версия, `new|reuse`, поколение, backend project ID/ожидаемый database origin, control project ID/origin и снимки/хэши серверного контракта. Публичные Firebase-настройки разрешены; credentials остаются вне Git.
- Отдельные источники служебного Hosting и статусов поколений; вывод backend и control не смешивается в одном deploy config.
- Локальный план ротации с этапами и точным выбранным поколением/project ID; факт облачного результата записывается только после его проверки.

Точные filenames операторского CLI можно уточнить без изменения контракта. Его минимальные действия: validate/plan для релиза и ротации, prepare control/backend, отдельные явные deploy/retire/provision с возможностью продолжить тот же план. Число проектов нельзя проверять только по доверенному локальному JSON: перед облачным изменением сверяются фактические ID/состояния и принадлежность поколению. Неизвестное расхождение останавливает операцию.

Процесс рассчитан на одного оператора с одним актуальным инвентарём. CLI сериализует локальные операции над планом, сохраняет ожидаемую revision реестра и перепроверяет её и фактические проекты перед изменением. Параллельное независимое управление из разных checkout не поддерживается: при расхождении операция останавливается. Распределённый управляющий сервис в change не добавляется.

Публичный реестр на `/backend-generations.json` содержит `schemaVersion: 1`, монотонный `revision`, `updatedAt`, записи `{ generation, firstRelease, state }`, где state — `active|retired`; retired дополнительно имеет `retiredAt`. Допустимое будущее смещение времени до 5 минут; дубликаты, неправильные даты/версии/состояния и неизвестная схема отклоняются. У активных записей не больше трёх поколений. Отметки retired сохраняются при следующих публикациях; поколение не возвращается в active и его ID не используется заново.

В отличие от временного service status, у постоянного реестра нет обязательного ежедневного TTL. Старый по дате, но корректный заново полученный документ по-прежнему подтверждает необратимую отметку retired. Ограничение актуальности относится к локальному результату запроса (до 60 секунд); по его истечении нужен новый запрос, а при ошибке результат неизвестен. Просроченный локальный cache не подтверждает новое решение интерфейса. Так статическому реестру не нужна фоновая служба только ради продления отметок об отключении; временные quota/maintenance объявления сохраняют прежний TTL.

Реестр не содержит API keys, адресов базы, room keys, executable code или указания переключить backend. Клиент подключается исключительно к конфигурации своего поколения, встроенной при сборке. Public JSON — источник диагностики/поддержки, не источник полномочий.

### 4. Постоянное приглашение содержит поколение во fragment

Новый адрес: `<control-origin>/#generation=g0002&room=<secret>`. Разрешены ровно два поля, без дубликатов; origin/path/sender/frame проверяются как сейчас. Произвольный backend URL, project ID или версия из query не принимаются. Конкретное поколение копируется из конфигурации создания; при входе совпадение проверяется с metadata после свежего чтения.

Страница служебного Hosting получает небольшой bundled статический script только для проверки публичного реестра и отображения прекращённой поддержки, в том числе без расширения. Он читает из fragment только поколение, не отправляет fragment наружу, не использует Auth/RTDB, analytics или произвольные ссылки из JSON. Сохраняются no-referrer и строгая CSP с локальным `script-src 'self'` и запросами только на свой origin. При неизвестном статусе остаётся честная установка/повтор, без ложного сообщения об удалении.

Manifest, static content-script matches, `frame-ancestors` и web-accessible resources разрешают точный постоянный origin. Не добавлять wildcard всех web.app, все исторические проекты или удалённый код. Внешняя страница не получает ключи/токены через extension messages; секрет обрабатывается в доверенном extension iframe по существующей модели.

Поддержка legacy `#room=` на старых project origins не добавляется. Их нельзя сделать постоянными без отдельной совместимости/redirect инфраструктуры. Этот bootstrap-предел явно описывается в runbook, privacy и критериях приёмки.

### 5. Проверка поколения предшествует сетевому входу

Порядок для нового приглашения:

1. Проверить origin, fragment и формат generation/key.
2. При чужом поколении — только публичная классификация по реестру, без Firebase Auth, чтения комнаты и открытия watch-вкладки.
3. Для своего поколения сначала разрешить локальную активацию уже связанной вкладки, как в `handle-service-capacity`.
4. При новом соединении проверить реестр и публичный статус своего поколения внутри прежнего общего срока 15 секунд; затем Auth и точный REST read, проверка metadata, открытие просмотра.

Реестр и status читаются независимо, по возможности параллельно, каждый с пределом 3 секунды, singleflight и интервалом не меньше 30 секунд на документ. Cache не больше 60 секунд/TTL. Отмена обрывает запросы, поздний результат не открывает вкладку. Эти проверки не добавляют realtime-соединения и не продлевают общий срок.

Решения интерфейса:

| Ввод/результат | Поведение |
| --- | --- |
| Своё поколение, корректный контракт | Обычный вход и существующие retry/cancel |
| Своё поколение, реестр недоступен/просрочен/не знает запись | Ограниченный вход по встроенной конфигурации, без утверждения об удалении |
| Чужое active, первый релиз новее клиента | Предложить обновить расширение и открыть приглашение снова |
| Чужое active старше либо чужое неизвестно | Объяснить неподдерживаемую версию; предложить создать новую комнату |
| Подтверждённое retired любого поколения | Поддержка завершена; без автоматического восстановления; при retired собственного поколения сначала обновить расширение, затем создать новую комнату |
| Свежая комната не соответствует generation/metadata | Неподдерживаемая комната; без presence, сохранения или исправления данных |

«Создать новую комнату» — инструкция открыть нужное видео и воспользоваться обычным действием расширения. Приглашение чужой комнаты не раскрывает её videoId без чтения чужого backend, поэтому мгновенное создание из него не обещается. Никакой автоматической комнаты или миграции.

Если само встроенное поколение уже retired, создание в нём также блокируется до Auth/записи; кнопка создания не должна заводить пользователя в тот же отказ по кругу. Сначала предлагается обновление до поддерживаемой версии, затем обычное создание. Это проверяется и в прямом действии popup «Смотреть вместе», а не только при приёме приглашения.

### 6. Metadata и серверный контракт фиксируются на поколение

Новая metadata: `{ name, createdWithVersion, backendGeneration }`, strict. Версия — текущий формат пакета из трёх числовых компонентов; сравнение для диагностики — числовое по компонентам, не по строке. Сервер проверяет форму версии и неизменность metadata; значение не является криптографическим доказательством версии исполняемого клиента.

Генератор Rules фиксирует конкретный `backendGeneration`, запрещает чужой при создании и изменение metadata после создания. Не ослабляются существующие ограничения Auth, room key, playback/revision, server time, presence ownership и запрет перечисления. Emulators/QA получают собственные тестовые значения.

Снимки production Rules и описания контракта сохраняются по поколению, а не заново берутся для старого поколения из актуальной ветки. Deploy по описанию нового релиза не может нацелиться на чужой project ID. `reuse` не требует deploy нового серверного контракта; эксплуатационная правка старого поколения использует его собственные артефакты и отдельную явно выбранную операцию.

Первое внедрение — новое поколение и новый проект. Действующий production учитывается в инвентаре как legacy-поколение первого релиза 0.1.0; его Auth, Rules, данные и Hosting не переписываются. Новые клиенты его комнаты не читают.

### 7. Каталог и привязки не мигрируют

Namespace каталога и bindings включает окружение, поколение и версию локального формата. Все room-bearing messages и сравнения существующих вкладок учитывают поколение вместе с key. Совместимые релизы одного поколения сохраняют namespace и записи. Для несовместимого поколения старые namespace не читаются ради восстановления/переноса; старые записи не превращаются в частично распарсенные записи нового формата.

Добавление generation в новые записи не означает поддержку исторических локальных форматов. Обновлённый worker/session не возобновляет старую привязку, не создаёт presence и не отправляет отложенные команды. Проверяются reload, runtime update и worker restart, включая поздние сообщения старого target. Если runtime API сообщает об обновлении контекста, просмотр остаётся локальным до нового явного создания/входа.

### 8. Статус поколения отделён от его поддержки

Существующая JSON-схема operational/busy/unavailable сохраняется; endpoint теперь `<control-origin>/generations/<generation>/service-status.json`. Объявление инцидента относится ровно к одному поколению. `retired` хранится в реестре, не маскируется под maintenance/quota и имеет приоритет при новом входе/reconnect.

Исправный просмотр не получает постоянного polling и не отключается из-за запоздалого объявления. При фактическом отключении backend начнётся обычный цикл восстановления, в котором свежая отметка retired остановит повторы. Если реестр недоступен, действуют прежние ограниченные попытки и нейтральная ошибка. Мгновенное уведомление всех уже открытых вкладок не обещается.

Служебная Hosting-подготовка всегда собирает весь набор реестра, privacy, installation state и generation-status из сохранённого источника. Публикация одного status не должна стереть остальные или retired-записи. Сохраняются CORS/no-store/nosniff и отсутствие токенов/секретов в выводе.

### 9. Ротация — последовательность с сохранённым планом

Учитываются все ещё используемые или подготовленные backend-проекты, а не только последний published-релиз. `planned` без ресурса не занимает место; `provisioned`, `active` и `retiring` занимают. После проверенного `DELETE_REQUESTED` проект не является работающим backend, но отдельно остаётся в облачной квоте. Окончательное удаление не подменяется локальной отметкой.

При трёх проектах порядок строго такой:

1. Проверить инвентарь, фактические проекты, роли и квоту, записать новый план. Старейший выбирается по `firstRelease` численно; её нельзя менять patch-релизом. Неоднозначные/дублированные первые версии останавливают план.
2. Подготовить retired старейшего поколения в служебном источнике, опубликовать и проверить публичный ответ нужной revision. Остальные поколения и статусы сохранены.
3. По тому же плану запросить удаление точного project ID, перепроверить его состояние. Ошибка прав, несоответствие или неизвестный исход останавливают дальнейшие действия. Повтор не выбирает следующую жертву.
4. Только после подтверждённого запроса удаления и повторной проверки доступной квоты создать новый проект. Состояние provisioned уже занимает освободившееся место. Повтор сначала проверяет, не создан ли проект этим планом.
5. Развернуть собственные Auth/Rules нового поколения, пройти smoke, подготовить пакет. Опубликовать active нового поколения только после готовности backend. Chrome Web Store review/publish — отдельные этапы; реестр не объявляет неопубликованный пакет установленным пользователям.

Если проектов меньше трёх, этапы 2–3 пропускаются без удаления. Действующий QA, control и произвольные неучтённые проекты не становятся кандидатами удаления. Ошибка создания после удаления не запускает ротацию второго старого поколения: остаются два работающих backend и незавершённый тот же план.

Firebase/Google Cloud оставляет удаляемый проект в квоте до 30 дней; ID проекта не переиспользуется, а восстановление проекта не гарантирует возврат всех ресурсов. Это внешнее ограничение, поэтому проверка квоты предшествует разрушительному этапу и повторяется перед созданием; при невозможности создания оператор ждёт или отдельно решает вопрос квоты. Нельзя обходить лимит дополнительным удалением. Основание: [Firebase projects](https://firebase.google.com/docs/projects/learn-more), [Google Cloud: delete/restore](https://docs.cloud.google.com/resource-manager/docs/delete-restore-projects), проверено 2026-11-04.

## Risks / Trade-offs

- [Обновление расширения делает прежнюю комнату недоступной этому клиенту] → принято пользователем; объяснение и новая комната, без миграции или автоматического downgrade.
- [Старые project-origin ссылки исчезнут при удалении legacy] → явно ограничить обещание постоянных ссылок новыми приглашениями; старый production не переделывать ради совместимости.
- [Control Hosting — общая зависимость диагностики] → ограниченный таймаут и fail-open только для своего встроенного backend; сбой реестра не становится ложным retired/quota. Реальный доступ комнаты по-прежнему ограничен Rules.
- [Кэш реестра задерживает обнаружение новой ротации] → HTTP no-store, локальный результат до 60 секунд и перепроверка при следующем действии; существующая active-запись не гарантирует успешное соединение. Постоянные retired-отметки не требуют ежедневного продления.
- [Новый control origin меняет manifest permissions] → проверить точные host permissions, matches, CSP, Store disclosures и поведение обновления/повторного разрешения. Chrome документирует предупреждения при изменении host_permissions/content_scripts.matches: [Declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions). Не обещать незаметное обновление.
- [Ротация отключает старые комнаты до доступности нового пакета в Store] → это следствие правила «удалить до четвёртого проекта»; отдельно показывать review/published/backend-ready состояния, не объявлять полный выпуск по одному deploy.
- [Локальный инвентарь устарел или проект восстановлен вручную] → сверка фактического состояния перед каждым внешним изменением, блокировка противоречия и проверка реального числа работающих backend.
- [Ошибка общего Hosting deploy стирает статусы] → собирать полный control output, сохранять retired/инциденты и проверять независимость на fixtures до реального rollout.

## Migration Plan

### Локальная реализация

Выполнить задачи контрактов, UI, конфигурации и операторских проверок; использовать эмуляторы, QA-конфигурацию и адаптер облачных операций на fixtures. Не менять реальные проекты, локальные production credentials, Store item и существующий `.env.production` автоматически. Проектные документы и ADR обновить по результату реализации; старые архивы OpenSpec не переписывать.

### Отдельный rollout

1. Сверить фактическое состояние `prepare-public-release` и Store, текущие проекты и квоту. Не считать имеющиеся записи runbook свежей live-проверкой.
2. Создать отдельный служебный проект и новый backend, записать настоящие ID/origin. Учесть legacy в тройке, не удаляя его при наличии свободного места.
3. Опубликовать постоянную страницу/privacy/реестр и статусы, развернуть только новый контракт нового backend; проверить привязку/отказы доступа и два профиля.
4. Собрать и повторно аудировать release ZIP с точными generation/project/control mappings, версией, commit и SHA-256. Обновить Store privacy URL/disclosures и отдельно загрузить в существующий item.
5. После review и явной публикации проверить установку, приглашение и управление. Только наблюдаемые результаты фиксировать как выполненные; pending/review и skipped не закрывают приёмку.

При первом rollout будет два backend (legacy + новый) и отдельный control, поэтому ротация/удаление не нужна. Удаление legacy не является задачей первого выпуска.

### Откат

До внешней публикации убрать неготовый кандидат из плана без воздействия на работающие поколения. Уже созданный кандидат продолжает учитываться, пока его удаление не проверено. Для control откат допустим только с сохранением всех уже опубликованных retired-отметок; старый snapshot, возвращающий retired в active, неприемлем.

Отменённый release не переносит комнаты в старый backend. После запроса удаления не обещать восстановление данных; отказ от ротации не должен молча публиковать active для удалённого проекта. Ошибку исправлять по фактическому состоянию и отдельному операторскому решению. Откат расширения через Store — новый проверенный пакет с допустимым номером, а не перепубликация меньшей версии.

## Проверяемые гипотезы и условия пересмотра

- **Пока не проверено:** разделение database/control origin проходит Auth/REST/iframe CSP в реальном Chrome. Критерий — локальная браузерная матрица плюс отдельный live QA smoke; при неуспехе исправлять точные разрешения, не добавлять общий wildcard.
- **Пока не проверено:** оператор имеет права и квоту на служебный проект и дополнительный backend. До разрушительной ротации нужен успешный preflight; отсутствие прав/квоты блокирует rollout, а не меняет автоматически тариф или число поддерживаемых поколений.
- **Пока не проверено:** поведение обновления расширения с новым Hosting origin и старыми session bindings. Критерий — нет автоматического входа старой сессии, чужих запросов и ложного успеха; сценарий повторного разрешения в Chrome записывается отдельно.

Конкретные новые project IDs, следующий releaseVersion и доступность Store review — операционные параметры rollout. Они не блокируют реализацию и проверяются перед реальными облачными действиями, а не выдаются здесь за существующие ресурсы.
