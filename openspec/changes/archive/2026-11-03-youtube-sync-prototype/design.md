# Design: Технический прототип

## Context

Мотивация и границы — в [proposal](proposal.md), продуктовые сценарии — в [PRD](../../../../PRD.md). Технический прототип принят 2026-11-03, 22/22 задачи. [ADR-0002](../../../../docs/adr/0002-firebase-room-backend.md) и [ADR-0003](../../../../docs/adr/0003-native-youtube-player.md) приняты для прототипа; естественная реклама отложена пользователем. Исторические результаты ниже сохранены, итоговая приёмка описана перед Risks / Trade-offs.

## Goals / Non-Goals

Архитектурная цель: отделить алгоритм общего воспроизведения от Firebase, DOM YouTube и UI, чтобы гонки и восстановление можно было воспроизвести без сайта.

Прототип проверяет два независимых профиля; расширение не занимается видеотранспортом. Production lifecycle пустых комнат и окончательная организация всех комнат не входят в это изменение.

## Decisions

### Разделение ответственности

- Адаптер плеера читает локальное состояние, обнаруживает пользовательские действия, применяет удалённые команды и определяет локальные ограничения.
- Sync engine вычисляет целевую позицию, подавляет повторные события, согласует версии и управляет reconnect.
- Room transport обслуживает Auth, состояние и presence.
- UI показывает комнату, число участников, соединение, локальные ограничения и выход.
- Service worker управляет вкладками и короткими browser-событиями; его непрерывная жизнь не предполагается.

Альтернатива — единый content script со всем кодом — затруднит воспроизведение гонок и замену интеграции с YouTube.

### Проверка контекста Firebase — первая техническая задача

До основного кода сравниваем extension-origin документ, связанный с открытой вкладкой просмотра, и соединение в восстанавливаемом service worker. Проверяем доступность SDK/Auth, CSP, единство анонимного UID и остановку worker. Подход выбирается по результатам и заносится в ADR-0002.

Если для документа нужен iframe или bridge, он содержит только минимально необходимый extension-код; идентификаторы и токены авторизации не передаются скриптам страницы. У каждого room session явно определён владелец соединения и очистка ресурсов.

Это запланированный эксперимент, а не отложенный выбор на этапе реализации всего транспорта. При отсутствии работающего варианта сначала пересматривается design.

Результат задачи 1.3: выбираем bundled extension-origin документ в iframe вкладки просмотра. Он владеет RTDB-подписками независимо от popup и worker. Общий UID хранится через `indexedDBLocalPersistence`; инициализация Auth и первый вход сериализуются Web Lock между контекстами. RTDB работает только через WebSocket (`forceWebSockets()`), поскольку JSONP long polling несовместим со строгим MV3 CSP. Worker может восстановить UID и актуальное состояние после явного пробуждения, но не является владельцем постоянного соединения. Матрица локального стенда и границы проверки записаны в ADR-0002 и отчёте; bridge с content script, Rules комнат и реальный YouTube ещё предстоят.

### Реализация Auth и transport — задача 2.1

Основной `src/` содержит общий Firebase-клиент и transport чтения комнаты, `.info/connected` и `.info/serverTimeOffset`. Popup просит isolated content script создать iframe, получает только публичный случайный адрес документа и далее обращается к нему через `runtime.sendMessage`. Session принимает строго проверенные Zod-запросы только от собственного `popup.html`; content scripts, сайт и другие extension pages не могут выбирать комнату или читать UID/данные. В URL iframe нет секрета/UID.

Один transport принадлежит одному документу. При смене комнаты снимается прежняя подписка, поздние callbacks отсекаются поколением; при pagehide снимаются все подписки и закрывается SDK-клиент. Отказ Auth отображается с действием «Повторить». Обычная сборка без конфигурации не обращается к Firebase; `WXT_FIREBASE_EMULATORS=1` подключает только локальный demo-проект и отдельный output. Облачная конфигурация добавляется отдельно. Модель playback, запись команд, создание и восстановление привязки комнаты и presence относятся к следующим задачам.

### Создание комнаты — задача 2.3

Popup по действию «Смотреть вместе» запрашивает снимок плеера у isolated content script конкретной вкладки и пересылает его session-документу. Оба получателя проверяют собственный popup как отправителя; запрос снимка дополнительно содержит текущий публичный адрес session. Content script кратко создаёт существующий DOM-адаптер, читает его и сразу освобождает; `onIntent` ничего не отправляет. Допускается только `ready` без незавершённого seek, поэтому реклама, live с бесконечной duration, ошибка и загрузка не сохраняются как исходное видео. Zod на границе записи проверяет только videoId, positionSeconds, playbackRate и isPlaying; личные и серверные поля в запросе запрещены. Полная модель playback и вычисление целевой позиции остаются задачей 3.1.

Session создаёт 256-битный секрет через `crypto.getRandomValues`, кодирует его в 64 hex-символа и записывает `{ playback }` с revision=0, собственным actorUid, случайным commandId и `serverTimestamp()`. При отсутствии соединения новая запись не начинается. Ссылка выдаётся после подтверждения `set`, после чего transport подписывается на созданную комнату. Незавершённые и повторные create-запросы одного документа используют одну операцию/комнату. При отказе записи показывается ошибка, повтор разрешён. Закрытие popup не останавливает сессию; при следующем открытии возвращается её приглашение. Восстановление привязки после reload — отдельная последующая задача.

Базовый URL приглашения берётся из конфигурации, секрет хранится только в `#room=<secret>` и не добавляется в URL iframe или DOM YouTube. Пока настроен только loopback Hosting `http://127.0.0.1:5002/`; HTTPS origin облачного приглашения ещё не настроен. Страница входа и проверка её origin относятся к 2.4. Копирование выполняет popup через Clipboard API с manifest-разрешением `clipboardWrite`; при отказе остаётся поле для ручного копирования. `clipboardRead` в manifest отсутствует.

### Страница приглашения — задача 2.4

Локальная Hosting-страница не использует Firebase или сторонние скрипты. По умолчанию она показывает инструкцию установки unpacked-прототипа; ссылки на несуществующую публикацию в Web Store нет. CSP запрещает скрипты, сеть, формы и embedding самой страницы; разрешены локальный CSS и extension iframe, Referrer-Policy — `no-referrer`.

В локальной сборке isolated content script обслуживает только верхний frame точного `http://127.0.0.1:5002/`, без query, credentials и других путей. Он создаёт закрытый Shadow DOM с `invitation.html#<public UUID>` и передаёт текущий секрет внутренним runtime message. Адрес iframe не содержит секрета. Получатель проверяет собственный extension ID, наличие tab ID, frameId=0, доверенный URL отправителя, публичный target и строгую Zod-схему. Content script принимает только один параметр `room` во fragment, включая проверку полного ключа; повторные и неизвестные параметры недействительны. `sender.url` Chrome сохраняет исходный fragment документа, поэтому текущий fragment читает content script и повторно доставляет при `hashchange`. Сайтового `postMessage`-bridge и `externally_connectable` нет; обратный ответ содержит только `{ accepted: true }`.

После явного клика в extension iframe transport выполняет Anonymous Auth и подписку на существующую комнату, ничего в неё не записывая. UI показывает отсутствие комнаты, ошибку доступа/Auth или проверенное начальное playback-состояние; последующие обновления читаются той же подпиской. При смене fragment старая подписка снимается, UI очищается и требуется новый клик. При pagehide закрываются подписки и SDK. В обычной сборке invitation entrypoints и локальные разрешения отсутствуют; облачный HTTPS origin ещё не настроен.

В 2.4 документ входа временно владеет чтением комнаты на странице приглашения. Presence добавляется в 2.5; открытие/повторное использование watch-вкладки и перенос владения сессией — в 2.6. Применение состояния к плееру и расчёт позиции — блок 3. Кнопка подтверждает подключение к данным комнаты, а не готовность полного совместного просмотра. Основной `session.html` по-прежнему принимает команды только от popup; доверие к invitation content script не расширяет этот API.

### Присутствие — задача 2.5

После получения действительной комнаты transport публикует `presence/<uid>/connections/<connectionId> = { connectedAt: serverTimestamp() }`. `connectionId` — случайный UUID отдельного соединения extension-документа. Перед записью сервер подтверждает `onDisconnect().remove()`. При reconnect создаётся новый connectionId и заново регистрируется уборка. При выходе, смене комнаты и закрытии документа старое соединение удаляется; отмена `onDisconnect` выполняется после подтверждения удаления и завершения регистрации. Отложенный SDK set при обрыве сопровождается следующим за ним remove старого пути, поэтому он не восстанавливает ушедшего участника поверх нового соединения.

Несколько документов одного UID считаются одним участником, пока у него есть хотя бы одно соединение. Список UID сортируется одинаково у всех клиентов; порядковый номер и цвет вычисляются из индекса. Отметка «вы» сравнивается с собственным UID; UID в UI не выводится. Номера уникальны в текущем составе, но при его изменении номер и цвет могут меняться: стабильность после возвращения из PRD проверена и пока не обеспечивается. Постоянное резервирование номеров не входит в этот прототип.

Индикатор, popup и страница приглашения показывают список, число участников и выход. При отсутствии связи список скрыт; ошибки регистрации presence имеют повтор подключения. Выход снимает room subscription и только собственное соединение документа; playback и остальные UID не меняются. Серверное право второго UID изменять playback после выхода создателя проверяется отдельно от будущего sync engine. До 2.6 приглашённый участник представлен документом страницы приглашения.

### Связанная вкладка — задача 2.6

После проверки комнаты extension iframe приглашения передаёт worker строго проверенный запрос с ключом и videoId. Worker принимает его только от собственного адресованного `invitation.html` во вкладке доверенного Hosting. Запрос не позволяет выбирать произвольный URL или tab ID. Операции сериализованы: повторные и одновременные приглашения активируют одну связанную вкладку, включая вкладку создателя; окно этой вкладки получает фокус. Если связанная вкладка ушла с общего видео, при повторном приглашении она открывает URL общего ролика.

Привязки tab ID → ключ/videoId/публичный target хранятся в `chrome.storage.session` с новым manifest-разрешением `storage`. Постоянного Firebase-соединения у worker нет; остановка worker не стирает привязки. Для новой вкладки сначала создаётся `about:blank`, сохраняется привязка, затем открывается YouTube. При ошибке открытия новая вкладка и её привязка убираются. После закрытия вкладки `tabs.onRemoved` удаляет запись. Между полными перезапусками браузера реестр не сохраняется.

Isolated content script при загрузке узнаёт только boolean наличия привязки. Перед embedding он регистрирует случайный target своего session iframe; worker принимает регистрацию лишь от верхнего content frame YouTube. `session.html` получает ключ непосредственно от worker при совпадении extension ID, URL, tab/frame и зарегистрированного target. Посторонний iframe с другим target не получает привязку. Секрет не добавляется в URL YouTube/iframe, DOM страницы или ответ content script. Session подписывается на актуальные данные комнаты и создаёт presence. Документ приглашения снимает свою room subscription после открытия вкладки и сам presence не регистрирует.

После создания комнаты session регистрирует вкладку создателя. При reload связанная вкладка автоматически создаёт новый session iframe и получает актуальную комнату. Явный выход сначала удаляет сохранённый ключ, затем снимает подписку/presence; последующий reload не восстанавливает вышедшего участника. Назначение target сохраняется до уничтожения документа, чтобы можно было создать новую комнату без перезагрузки. Применение playback к плееру и вычисление целевой позиции остаются блоком 3.

### Состояние и порядок команд

Рабочая модель playback: videoId, positionSeconds, playbackRate, isPlaying, updatedAt, revision, actorUid, commandId. Presence хранится отдельно от playback; общие права не зависят от creatorUid.

Пользовательская команда несёт уникальный commandId и базовую revision. Транзакция проверяет текущую версию: если база совпадает, вычисляет новое состояние и увеличивает revision; иначе команда отклоняется как устаревшая, а клиент применяет актуальное состояние. При одновременных действиях из одной базовой версии принимается одно; повтор того же commandId не создаёт новую команду. Участник может повторить действие уже после получения новой версии.

Альтернатива с безусловным перезаписыванием упрощает код, но допускает возврат устаревших команд и затрудняет объяснение гонок. Правило текущего прототипа проверяется отдельно и может быть уточнено по результатам usability.

updatedAt задаётся сервером при принятии состояния. Воспроизводимая целевая позиция вычисляется от опорной позиции, скорости и прошедшего времени; оценка времени сервера и её погрешность измеряются. Локальная коррекция позиции не записывает новую команду в комнату.

Реализация 3.1: `src/lib/playback/model.ts` содержит общие `initialPlaybackSchema`, `playbackSchema` и типы; создание комнаты и проверка приглашения используют их без дублирования полей. Полная схема принимает числовой `updatedAt` после разрешения серверной метки; объект `serverTimestamp()` предназначен для записи transport и не считается принятым состоянием. Личные и неизвестные поля playback запрещены.

Чистая функция `targetPositionSeconds` получает проверенное playback-состояние, локальное время `nowMs`, смещение `serverTimeOffsetMs` и необязательную локальную `durationSeconds`. Для играющего видео позиция равна `positionSeconds + max(0, (nowMs + serverTimeOffsetMs - updatedAt) / 1000) * playbackRate`; для паузы остаётся опорной. Оба результата ограничены длительностью, если она известна, иначе — безопасным числовым диапазоном модели. Отрицательное прошедшее время не перематывает назад. Некорректные часы и длительность отклоняются; длительность не добавляется в данные комнаты. Функция не читает DOM/часы/Firebase, не меняет playback и не отправляет команд. В 3.3 расчёт подключён к адаптеру через sync engine.

Реализация 3.2: `createPlaybackCommand` создаёт строгую команду с полным общим снимком плеера, `baseRevision` и случайным UUID `commandId`. Повторная доставка сохраняет оба значения. Чистая `preparePlaybackCommand` проверяет текущее состояние, неизменность videoId и точное совпадение базовой revision; успешное решение увеличивает её на единицу. Переполнение безопасного диапазона запрещено. Совпадающий с текущим commandId признаётся `duplicate` только при совпадении автора, снимка и исходной версии; коллизия с другим содержимым отклоняется. После последующих команд повтор старой команды отклоняется по старой базе: история commandId не хранится и для этого не нужна.

`submitPlaybackCommand` выполняет `runTransaction` только на `rooms/<secret>/playback`, добавляя собственный actorUid и `serverTimestamp()` к решению чистой функции. Callback при повторном вызове не меняет baseRevision, поэтому проигравшая конфликт команда отклоняется и возвращает актуальное состояние. `applyLocally: false` скрывает промежуточные попытки от подписчиков. Временная подписка заполняет и удерживает cache SDK до окончания транзакции: иначе первый callback может получить null существующей комнаты. Она снимается при успехе, отказе или ошибке. На одном пути одного SDK-клиента разрешена одна незавершённая операция; следующая получает `busy` без очереди, чтобы не принять скрытую optimistic-запись за server ack. Отказ Rules выбрасывает ошибку и освобождает путь для следующего действия.

Transport предоставляет внутренний `sendCommand`: UID берётся из Auth, ключ — из активной подписки, а перед стартом и в callback проверяются готовность комнаты и поколения сессии/соединения. В 3.3 этот метод вызывает sync engine по проверенным пользовательским намерениям адаптера. Реализация 3.5 дополнительно передаёт AbortSignal: обрыв или выход отменяет ожидание начального snapshot, снимает временную подписку и освобождает путь. Проверка поколения помнит обрыв даже после быстрого reconnect. Отправленная SDK-транзакция может быть уже принята сервером; клиент не пытается отменить принятую запись или автоматически повторить действие. Реальный SDK и сервер проверяются при разрыве пакета транзакции до доставки и при потере ack после принятия, с последующей командой другого UID и без неё.

### Локальные состояния и reconnect

Реализация 3.3: независимый `createSyncEngine` живёт в session-документе рядом с transport. Он принимает только новые revision, рассчитывает позицию через серверное смещение и передаёт общий снимок плеера в content script своей вкладки через `tabs.sendMessage` с frameId=0. Content script проверяет extension ID, точный URL адресованного session iframe и строгую схему. Chrome не добавляет tab/frameId отправителя к этому виду сообщения; проверка не требует отсутствующих полей. Ответ применения также проверяется схемой. Обратные runtime messages принимаются session только от собственного верхнего content frame YouTube с совпадающими tab ID и target. Секрет, actorUid, Auth и revision в content script не передаются.

Адаптер создаётся при первом применении и работает до выхода/инвалидации; пользовательские intent передают общий снимок и получают текущую базовую revision в engine. Подтверждение собственного commandId не вызывает повторное применение; дубли room subscription от presence и старые версии игнорируются. При stale применяется последняя известная версия без повторной отправки проигравшего действия. Вторая локальная команда во время незавершённой записи не ставится в очередь; после подтверждения плеер возвращается к принятому состоянию. Смена комнаты и выход отсекают поздние результаты поколением сессии и освобождают адаптер.

Реализация 3.4: engine сохраняет локальную готовность отдельно от playback комнаты. Реклама, системная буферизация, autoplay-блокировка и другие ограничения запрещают исходящие intent и откладывают применение; новые revision заменяют сохранённую версию без очереди. После ready позиция пересчитывается из последней версии с текущим серверным временем, даже если во время ограничения новых команд не было. Счётчик переходов готовности сохраняет повтор, если ready пришёл раньше ответа blocked/replaced/timeout или ошибки применения.

Адаптер дополнительно передаёт признак localSeek для буферизации, вызванной подтверждаемым пользовательским seek. Такая буферизация не отменяет ожидающий debounce intent; допускается только этот seek. Если буферизация продолжается после его выдачи, восстановление ждёт подтверждения записи, чтобы не вернуть плеер к старой версии. Признак проходит строгую Zod-проверку во внутреннем bridge и не записывается в комнату. Основной session UI показывает локальные подсказки, в том числе «Нажмите play, чтобы продолжить», отдельно от состояния соединения. Первый разрешающий play не создаёт команду: после него применяется последнее play/pause комнаты. Полная матрица настоящего YouTube — 4.2.

Эксперимент 1.4 добавил `src/lib/player/youtube-player.ts` и отдельную сборку `experiments/youtube-player/`. Адаптер работает в isolated content script; первоначальный DOM-only setter скорости заменён в 4.4 узким MAIN-world bridge, описанным ниже. Capture-обработчики доверенных pointer/keyboard/input на конкретных контролах создают намерение play/pause/seek/rate, которое подтверждается соответствующим media-событием в течение 1500 мс. Seek объединяется до отпускания указателя и 120 мс без новых событий; возникшая от него буферизация не превращает seek в системное действие. Без конкретного намерения media-событие никогда не отправляется как команда. Произвольные клики, поиск и локальные настройки не открывают общее окно разрешения событий.

Скорость применяется через `#movie_player.setPlaybackRate()` в отдельном declarative content script с `world: MAIN`, `run_at: document_start`. Синхронный CustomEvent от текущего video передаёт только строгую Zod-модель `{ videoId, playbackRate }`. MAIN-listener заново находит root/video, сверяет URL и доступный getVideoData, готовность и отсутствие рекламы/ошибки. Он вызывает только setter скорости; preventDefault подтверждает совпадение `getPlaybackRate()` с запросом. Отсутствующий/сломанный API и неподдержанное значение дают `blocked`; прямого media fallback нет, иначе меню и первая горячая клавиша снова расходятся. Адаптер дополнительно ждёт фактического media-состояния 100 мс по прежнему протоколу. Getter/setter обычной watch-страницы — внутренняя зависимость YouTube, а не гарантия официального iframe API; нужна live-регрессия. В MAIN нет Firebase, UID, ключа комнаты, revision, browser API, очереди или обратного канала намерений. Поздних асинхронных setters нет; полномочия runtime messages не расширяются.

Удалённое применение сначала очищает старое намерение, затем устанавливает ожидаемую position/rate/play/pause до вызова setters. События подавляются до устойчивого совпадения на 100 мс либо ошибки/замены/прерывания/таймаута 3 с; после завершения требуется новый пользовательский ввод. Новое действие человека может прервать ожидающее применение. Адаптер возвращает результат операции, но не управляет revision и не хранит очередь команд. Sync engine позднее должен повторно рассчитывать применение из последней принятой версии после локального `blocked`.

Классы `ad-showing`/`ad-interrupting`, media waiting/readyState и привязка к videoId ограничивают локальную готовность. Замена root/video снимает старые listeners. Подробности и границы корреляции — в ADR-0003. На реальном YouTube подтверждены контролы и отсутствие обратных событий, а также локальность buffering при временном обрыве сети. Реальная реклама не появилась в выборке: задача 1.4 остаётся открытой. Замена DOM и реклама проверены на управляемом стенде; это не подтверждение соответствующих механизмов сайта.

Эксперимент 1.5 подтвердил реальный SPA-переход по рекомендации с сохранением root/video: фиксированный исходный videoId блокирует ввод/применение на другом ролике, Back возвращает готовность, диагностический UI даёт действие возврата к исходному URL. Ожидающее применение при переходе, ошибке, рекламе или autoplay-блокировке завершается `blocked`, а не ждёт таймаута. Видимые error/promo renderers внутри `ytd-watch-flexy` обнаруживают недоступность даже при скрытом плеере без MediaError; скрытые шаблоны не считаются ошибкой. Настоящий `NotAllowedError` проверен с browser policy без user activation; первый разрешающий play остаётся локальным, следующая пауза создаёт намерение. Это проверка адаптера и диагностического UI, без комнатного transport; последнее состояние комнаты после возврата применяет будущий sync engine. Подробности layouts и ограничений — в ADR-0003 и журнале.

Применяемая удалённая команда помечается до вызова методов плеера. Подавление обратной рассылки учитывает асинхронные события и достижение ожидаемого состояния; одного синхронного boolean недостаточно.

Буферизация, реклама, отсутствие готового видео и autoplay-блокировка приостанавливают локальное применение. Когда применение становится возможным, клиент использует последнюю принятую версию. Первый пользовательский клик может разрешить локальный play, не создавая новую общую команду при уже играющей комнате.

Реализация 3.5: `connected` отражает основное WebSocket-соединение, а `roomReady` разрешает синхронизацию только после свежего чтения комнаты. После выбора комнаты и каждого reconnect extension-документ создаёт временный Firebase app с Auth в памяти и копией действующего Anonymous User через `updateCurrentUser`; новый UID не создаётся. Его RTDB cache пуст, поэтому `get` читает сервер. `get`/`onValue` основного клиента могут вернуть cache активной подписки и не подтверждают свежесть. Секрет передаётся только внутри WebSocket-протокола, токен и ключ не добавляются в HTTP URL. Клиент чтения переводится offline и удаляется в finally. AbortSignal и таймаут 15 с ограничивают ожидание; обрыв, смена комнаты и выход отменяют чтение. При ошибке sync остаётся заблокированным, UI предлагает повтор подключения.

Если подписка успела принести более новую revision, поздний read не откатывает её. Presence остаётся за основной подпиской: у него нет playback revision и свежий снимок мог устареть к моменту доставки. При потере готовности соединения engine меняет поколение, освобождает ожидаемую команду и отключает адаптер, сбрасывая незавершённые intent/apply. Локальное воспроизведение продолжается; его изменения offline не накапливаются. Поздний успех или ошибка старой записи не влияют на восстановленный плеер. После server read применяется последняя версия с пересчётом позиции, включая прежнюю revision при отсутствии новых команд. Новое пользовательское действие получает актуальную базовую revision. Проверки фиксируют отсутствие отложенных записей в используемой версии SDK; внутренние API Firebase продукт не вызывает.

Реализация 3.6: громкость/mute, качество и субтитры не входят в общий снимок, команды или данные RTDB; строгие схемы и Rules отклоняют личные поля. Адаптер отдельно исключает DOM-контролы громкости, субтитров и их меню, меню качества: Arrow/Space на них очищают старое намерение и не прерывают удалённое применение. Без этого клавиша личного контрола могла разрешить последующее системное media-событие как общий seek/play/pause. Регрессия воспроизводится управляемым player-тестом; двухпрофильная проверка личных настроек находится в `tests/room-transport/local-settings.spec.ts`, включая opt-in настоящий YouTube. Выбранное качество проверяется по отмеченному пункту меню, поскольку фактическое разрешение при Auto может меняться самостоятельно.

### Приглашения и доступ

Используем HTTPS-страницу с секретом приглашения во fragment, чтобы он не попадал в обычный HTTP path/query и referrer. Расширение обслуживает только доверенный origin страницы приглашения и валидирует её сообщения. При отсутствии расширения страница показывает инструкцию установки.

Для прототипа проверяем модель RTDB с непредсказуемым секретом в ключе комнаты, запретом перечисления комнат, Auth и проверкой структуры данных. В комнате любой участник может управлять playback, но не менять чужое присутствие. Доступ не расширяется на другие комнаты. Одно лишь знание Firebase-конфигурации или получение UID не даёт права прочитать произвольную комнату.

Секрет передаётся только через пользовательское приглашение; журнал эксперимента не содержит его или auth-токенов. Для публичного MVP оцениваем срок жизни приглашения и необходимость отдельного механизма членства.

### Контракт RTDB Rules — задача 2.2

Комната хранится в `rooms/<secret>`; ключ соответствует `roomKeySchema`: 32–128 символов `A–Z`, `a–z`, `0–9`, `_`, `-`. Auth и полный ключ разрешают чтение этой комнаты и дочерних узлов. Корень, коллекция `rooms` и запросы к ней закрыты. Это доступ по секрету без отдельного membership: любой авторизованный клиент, которому передали полный ключ, получает одинаковые права. Неизвестный ключ допустимого формата возвращает `null`; некорректный ключ отклоняется. Проверка формата не обеспечивает случайность: генератор приглашений в 2.3 должен создавать криптографически случайный ключ.

Создание комнаты записывает `{ playback }`, без presence. Разрешение создания на родительском узле распространяется на дочерние записи, поэтому presence при создании запрещён, чтобы нельзя было подставить чужой UID. После создания запись всей комнаты и её удаление закрыты. Playback меняется по собственному пути, presence — по `presence/<auth.uid>`; атомарный `update` нескольких таких путей разрешён при соблюдении каждого правила.

Playback содержит ровно поля рабочей модели выше. `videoId` — 11 допустимых символов YouTube, позиция — число от 0 до `Number.MAX_SAFE_INTEGER`, скорость — число `0 < playbackRate <= 16` (техническая граница данных, не список скоростей UI), `isPlaying` — boolean. Начальная revision — 0, следующая — целое `previous + 1` в безопасном диапазоне JavaScript. `actorUid` совпадает с автором записи; `updatedAt` равен времени сервера `now` (клиент передаёт `serverTimestamp()`). `commandId` — 1–128 символов того же алфавита, что у ключа; он отличается от текущего. Общий `videoId` после создания неизменяем. Личные настройки и неизвестные поля запрещены; обязательные поля, playback и саму комнату нельзя удалять. Транзакции, базовая revision и клиентская обработка повторной доставки реализованы в 3.2, как описано выше; Rules не хранят историю commandId.

В 2.2 минимальная запись presence была `{ connectedAt: serverTimestamp() }`; в 2.5 она заменена на `{ connections: { <connectionId>: { connectedAt: serverTimestamp() } } }`. Только собственный UID может создавать, обновлять или удалять свои соединения. Время новой записи равно серверному `now`; время существующей записи можно сохранить при изменении соседнего соединения. Неизвестные поля комнаты, presence и соединений запрещены. Удаление своего presence не закрывает комнату и не отнимает управление у остальных. Локальные `_probes` сохранены для воспроизводимости экспериментов; cloud-скрипт 4.3 удаляет этот узел из публикуемых Rules.

### Испытательный стенд и доказательства

Vitest проверяет вычисление позиции, версии, idempotency, подавление обратной рассылки и reconnect. Emulator Suite проверяет Auth/Rules и реальные транзакции. Playwright запускает два независимых persistent profiles bundled Chromium и проверяет расширение на управляемом видеостенде.

Затем отдельно проверяем реальный YouTube в Chrome: кнопки и клавиатуру, рекламу, buffering, autoplay, SPA-переходы, закрытие popup, остановку service worker, перезагрузку вкладки и выход создателя.

Отчёт создаётся в docs/experiments/youtube-sync-prototype.md во время выполнения. В нём: окружение, выбранный Firebase-контекст, матрица сценариев, p95 задержки для ≥30 команд, расхождение позиции, условия измерения и ограничения. Цели из PRD — критерии оценки, а не уже достигнутые результаты.

Реализация 4.3: общий resolver публичной Firebase-конфигурации используется сборкой и runtime. Без конфигурации обычная сборка не подключает Firebase; флаг эмулятора имеет приоритет. Облачная сборка отдельная, invitation bridge ограничен настроенным HTTPS origin, CSP разрешает Auth и RTDB. `.env.cloud` не входит в Git; service accounts и административные токены в расширение не добавляются. `scripts/cloud.mjs` собирает расширение либо разворачивает Auth/Rules/Hosting в тестовом проекте.

Стенд `tests/cloud/playback.spec.ts` работает с настоящими YouTube, Anonymous Auth и RTDB в двух независимых profiles. Наблюдение trusted input/media находится только в тесте. Позиции снимаются через 3 с, p95 считается по командам без локальных ограничений. Все исходные сессии и исключения сохраняются; агрегация отдельно показывает незавершённые сценарии. На 40 пригодных командах из 77 получены p95 300 мс и максимум расхождения 0,180 с, но три длинные попытки остановились после сброса media на команде 24. Это ограничение для разбора в 4.4; общая приёмка и пересмотр ADR ещё не выполнены.

### Итоговая приёмка — 2026-11-03

Распознавание скорости дополнено физическими Shift+Period/Comma при русской раскладке: trusted жест разрешает ожидание ratechange, сам по себе не создаёт команду. Проверки текстовых полей, личных контролов и Ctrl/Alt/Meta сохранены. Английские и русские клавиши после удалённой скорости проверены на стенде и настоящем YouTube, с одним намерением/одной revision и без эха.

В обычном установленном Chrome два QA-наблюдателя в копии облачной сборки читают HTMLMediaElement и существующий read-only status API. Они не добавляют продуктовый канал команд или разрешения и удаляются пересборкой. Четыре видимых окна предотвращают замораживание status-вкладок. Итог: 48 команд, 31 пригодная, p95 227,90 мс, максимум расхождения 0,17791 с через 3 с; все 48 с верным автором, revision 33 → 81 без эха. 17 исключены по buffering и сохранены. Первая неполная попытка не объединяется с итоговой. [Методика и сырые данные](../../../../docs/experiments/youtube-native-acceptance-2026-11-03.md).

ADR-0002/0003 приняты для технического прототипа. Измерен один Mac и общий маршрут, независимые сети/географии не проверены. Длинный автоматизированный cloud E2E по-прежнему прерывается внешним сбросом около 60-й секунды даже без расширения/Firebase; причина различия с обычным Chrome не установлена. Это не объявляется исправленным продуктовым дефектом или успешным автоматизированным тестом. Обычная инструментальная приёмка завершена без сброса, критерии PRD не смягчены; исключение остаётся только для естественной рекламы.

## Risks / Trade-offs

Уточнение 4.4 (2026-11-02): пользователь временно исключил естественную рекламу из приёмки. Это не отменяет локальность рекламы и не подтверждает live-поддержку рекламных состояний. Остальные критерии не смягчены.

Успешный apply актуальной revision при готовом плеере очищает запрос повторного применения, возникший от его собственного buffering. Иначе `waiting → ready` запускал новый seek по кругу. Новая revision и ограничение, сохраняющееся к получению результата, не теряют восстановление; blocked/replaced/timeout по-прежнему повторяются после готовности.

Видимый `#movie_player .ytp-error-content-wrap` считается unavailable раньше loading, даже без MediaError и класса ytp-error. Скрытые шаблоны не мешают просмотру. Для unavailable тот же безопасный anchor на общее видео с target=_top показывает «Перезагрузить видео». Секрет не добавляется в URL; существующая привязка storage.session восстанавливает UID и последнюю revision после загрузки. Никаких автоматических перезагрузок или очереди действий нет.

Контрольный `scripts/youtube-delivery.mjs` запускает Chromium без расширения/Firebase и воспроизводит сброс около 60-й секунды видео. Это локализует сбой за пределами нашего transport/engine, но не устанавливает причину внутри YouTube/Chromium/сети. ADR-0002 принят для прототипа; ADR-0003 и 4.4 остаются открытыми до длинного live-сценария. Рассогласование нативной скорости разобрано отдельно: MAIN-world setter согласует меню и первую горячую клавишу с media, как описано выше. Подробности — в журнале, раздел 4.4.

- Изменения DOM и внутреннего поведения YouTube → изолированный адаптер и реальные проверки сайта.
- Неотличимые системные события → эксперимент до основной синхронизации; неподтверждённые случаи не маркируются успешными.
- Остановка MV3 worker → проверка выбранного контекста и восстановления.
- Автоматическая очередь Firebase при offline → контроль базовой версии и тест обрыва во время записи.
- Различные реклама и доступность видео → локальные состояния с понятным индикатором.
- Эмулятор не показывает облачную задержку → отдельные измерения на тестовом Firebase-проекте перед принятием результатов.

## Migration Plan

Миграции существующих пользователей и данных нет. Сначала локальные эмуляторы и unpacked build; тестовое облако подключается отдельно при доступности проекта. Публикация в Chrome Web Store и production deploy в это изменение не входят.
