# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md). Это план; описанные ниже изменения ещё не реализованы.

- `src/lib/firebase/client.ts` сохраняет Anonymous UID в IndexedDB. `readRoom()` создаёт временный Firebase App/RTDB-клиент с тем же User: это защищает от cache основного SDK, но открывает ещё одно realtime-соединение.
- `room/transport.ts` разрешает sync только после свежего чтения; использует поколения соединения/комнаты и AbortController. У чтения есть таймаут 15 с, но он начинается после получения клиента. Для первоначальных Auth/соединения общего deadline нет.
- `invitation/main.ts` после чтения открывает YouTube. `Catalog.tsx` уже сначала пытается активировать связанную вкладку; закрытая комната читается отдельно. Popup имеет собственный цикл опроса статуса session-документа.
- Ошибки Auth сводятся к общей строке; callback отказа подписки сообщает об отсутствии доступа без классификации причины. Существующие reconnect-тесты проверяют отсутствие offline replay и запрет sync до server read.
- Hosting — статические HTML/CSS. Разрешение на origin приглашения уже есть, но extension CSP `connect-src` его не включает. `release:deploy` разворачивает одновременно Auth/Rules/Hosting; операторскому обновлению статуса нужна отдельная команда только для Hosting.
- Активный `prepare-public-release` затрагивает Hosting/release/listing. Новый change использует существующие команды и контракт; его применение потребует пересобрать пакет и повторить относящиеся к нему release-проверки.

## Goals / Non-Goals

**Goals:** дать одному владельцу попытки управление сроком ожидания и отменой; получать актуальные данные без дополнительной realtime-сессии; объяснять подтверждённую недоступность через канал, не зависящий от RTDB.

**Non-Goals:** управлять глобальным числом допущенных участников, гарантировать места, определять остаток квоты по пользовательскому клиенту или гарантировать работоспособность Hosting при его собственной аварии. Лимит 100 подключений не превращаем в обещание конкретного числа комнат.

## Decisions

### 1. Типизированная причина и единая операция подключения

Внутренний результат содержит категорию (`network-or-timeout`, `auth-rate-limited`, `auth-failed`, `access-denied`, `not-found`, `unsupported-room`, `service-busy`, `service-unavailable`), этап, retryability и необязательное время следующей попытки. UI отображает фиксированные русские тексты; технические ответы SDK/HTTP не выводятся пользователю целиком.

Перегрузка/квота подтверждается только свежим операторским статусом либо однозначным публичным кодом провайдера. `.info/connected=false`, HTTP 401/403/429 или строка `permission_denied` сами по себе не доказывают исчерпание квоты: отказ доступа не преобразуется в «мест нет». Конкретные Auth-коды сопоставляются по документации/фактическому ответу установленного SDK. При неоднозначном ответе остаётся нейтральная ошибка.

Один дедлайн 15 с охватывает получение Auth, ожидание соединения и обязательное свежее чтение одной попытки входа/восстановления. Загрузка статуса имеет отдельный предел 3 с и укладывается в этот же бюджет; она не добавляет ещё 3 с к deadline. UI не ждёт бесконечно незавершённый Promise SDK. Отмена/generation блокируют поздние continuation; поздно созданный ресурс освобождается его владельцем. Закрытие popup не закрывает соединение другой действующей watch-сессии.

Создание комнаты и пользовательские команды не повторяются автоматически. Истечение UI deadline не означает отмену уже принятой записи Firebase: показываем неопределённый результат, если ack потерян; сохраняем ключ незавершённого создания для проверки перед явным повтором вместо создания дубликата. Существующие правила commandId/revision и reconnect остаются обязательными.

Альтернатива — менять только текст общих ошибок — оставляет бесконечное ожидание и смешивает доступ с перегрузкой.

### 2. Ограниченные повторы и отмена

Для временного сбоя входа/чтения или восстановления — первоначальная попытка и не более четырёх автоматических повторов. Базовые задержки 10, 20, 40, 60 с плюс случайная добавка 0–20%; UI показывает округлённое оставшееся время. Свежий `busy.retryAfterSeconds` может увеличить задержку до 300 с; счётчик попыток всё равно ограничен. Ручное «Повторить» отменяет старую операцию и начинает одну новую серию; быстрые клики не создают параллельных попыток.

Внутри активной попытки reconnect делает SDK. После deadline владелец приостанавливает принадлежащее ему realtime-соединение на cooldown, затем возобновляет его: второй цикл поверх продолжающегося SDK reconnect не запускается. Успешное соединение ещё не успех входа: нужны свежее состояние и действующая операция. После исчерпания повторов остаются ручной повтор и отмена ожидания.

Отказ доступа, отсутствующая/неподдерживаемая комната, ограничение создания Auth-аккаунтов и `unavailable` не запускают автоматическую серию. Для Auth rate limit показываем «Слишком много попыток входа. Попробуйте позже», без придуманного срока сброса. Для `unavailable` ручной повтор сначала перепроверяет статус; пока он свежий, новая попытка RTDB не начинается. По истечении срока статуса причина становится неизвестной и допустима обычная ограниченная попытка.

«Отмена» у нового входа снимает подписки, таймеры и временные ресурсы; приглашение и сохранённая запись остаются. У уже связанной watch-вкладки отдельное «Остановить попытки» приостанавливает восстановление, сохраняя привязку; «Повторить подключение» возобновляет его. «Выйти из комнаты» сохраняет прежнюю семантику. Закрытие документа/смена target отменяют его операции. Browser timer throttling допускается: countdown считается от абсолютного времени, просроченные таймеры не проигрываются пачкой.

### 3. Публичный операторский статус на существующем Hosting

Фиксированный URL: `new URL('/service-status.json', invitationBaseUrl)`. Запрос из extension-контекста, `credentials: omit`, `referrerPolicy: no-referrer`, `cache: no-store`, без query, UID, ключа комнаты, Auth token и пользовательского текста. Разрешаем только этот уже настроенный origin в extension CSP; новых доменов и wildcard permissions не добавляем. Сам статус — данные, не remote code.

Версия контракта 1: `version`, `state: operational|busy|unavailable`, `updatedAt`, `expiresAt`; для `unavailable` обязательный `reason: maintenance|quota`, для `busy` необязательный `retryAfterSeconds` 10–300. Времена — UTC ISO; срок не больше 24 ч, `updatedAt` не более чем на 5 мин в будущем. Неизвестная версия/структура, просроченный статус, HTTP-ошибка или таймаут дают локальное `unknown`. Произвольные HTML, URL и сообщения не выполняются и не отображаются.

Свежий `busy` откладывает новые подключения по retry-политике; `unavailable` оставляет ручную перепроверку. `operational` означает отсутствие объявленной проблемы, но не гарантирует вход и не скрывает реальную ошибку доступа/сети. Уже работающие комнаты статус не отключает. Если соединение и свежее чтение фактически успешны, запоздавший ответ статуса не переводит их в ошибку.

Запрашиваем статус при явном начале входа/создания и после неудачи, когда нет актуального локального результата; при ожидании повторно проверяем перед очередной попыткой. Дедупликация и интервал не меньше 30 с на документ, включая ошибочные запросы. Кэш ограничен 60 с и `expiresAt`; ручная перепроверка не обходит 30-секундный предел. Здоровая активная сессия и простой просмотр локального каталога не опрашивают статус постоянно.

Источник — `firebase/hosting/service-status.json`; операторская команда готовит валидный файл и Hosting output, затем отдельный явный deploy публикует только Hosting выбранного production-проекта. Обычная release-сборка копирует этот файл, не заменяя активный инцидент на `operational`. Для JSON задаются `Content-Type: application/json`, `Cache-Control: no-store`; текущие CSP/no-referrer/nosniff остальных страниц сохраняются. Инструкция содержит проверку публичного файла после обновления и восстановление `operational`.

Альтернативы: RTDB-узел статуса требует того же дефицитного подключения; отдельный backend добавляет эксплуатацию и расходы. Hosting достаточно для ручного сигнала, но не является независимой инфраструктурой от всего Firebase.

### 4. Свежее чтение через REST с прежним UID

Вместо временного App получить Firebase ID token действующего User и выполнить отменяемый HTTP GET ровно `/rooms/<validated-key>.json?auth=<ID_TOKEN>` на настроенном database origin, с `cache: no-store`, `credentials: omit`, `referrerPolicy: no-referrer`. Токен не сохраняется отдельно и не передаётся content script/странице. Только Auth SDK управляет его обновлением. Запрос не использует Admin credentials и подчиняется текущим Rules.

REST не имеет cache SDK и не создаёт дополнительного realtime WebSocket. Основной клиент остаётся единственным владельцем подписок/presence; invitation и popup, которым нужно только чтение, не заводят realtime-подписку ради проверки. В transport свежее REST-чтение и подписка могут прийти в любом порядке: сохраняются сравнение playback revision, presence из подписки и проверки поколения. Abort/таймаут/выход запрещают позднее `roomReady` и открытие вкладки. Ошибка чтения не снимается последующим cache-event подписки.

Необходимые изменения: убрать временный Firebase App из `client.readRoom`, перевести invitation-проверку на read-only путь, сохранить Auth без нового Anonymous sign-in. При открытии существующей связанной вкладки сначала выполняется локальная активация, без REST/Auth ради повторного входа. Общий формат room и правила доступа не меняются.

Альтернатива — `get()`/`onValue()` того же SDK — может вернуть cache и ослабить существующий барьер свежести. Сохранение второго SDK-клиента сохраняет расход realtime-слотов. REST выбран по документированному пользовательскому ID-token доступу; CORS/CSP и фактический расход проверяем в браузере, а не считаем доказанными этим design.

### 5. Проверка результата

Unit с управляемым временем: классификация, 15/3-секундные пределы, лимит/jitter повторов, отмена/поздние Promise, истечение статуса. Emulator/Playwright: настоящий SDK/Rules, перехват сети для отказа/задержки, отсутствие второго realtime WebSocket на свежее чтение, отсутствие нового UID, duplicate presence и offline replay. Прежние reconnect-тесты, перехватывающие SDK `g`-пакет, адаптируются к REST-запросу; сценарии и проверки актуальности сохраняются.

Поддельный статус в тесте подтверждает UX, но не реальный Spark quota отказ. На отдельном QA-проекте допустим ограниченный smoke Auth/REST/reconnect и наблюдение соединений; production не заполняем искусственно до лимита. Реальный YouTube проверяется отдельно: потеря/возврат синхронизации и сохранение локального режима. Проверки, которые не удалось выполнить, остаются открытыми.

## Risks / Trade-offs

- [Hosting также может быть недоступен или исчерпать квоту] → `unknown` и встроенные нейтральные сообщения; вход не блокируется отсутствием статуса.
- [Ручной статус устаревает или оператор забывает его снять] → обязательные времена, TTL ≤24 ч, инструкция и ограниченный локальный cache. Клиент не обещает время восстановления.
- [REST auth token находится в query] → не логировать URL запросов/ответов, исключить network trace с секретами из артефактов; sanitised ошибки вместо сырых HTTP/SDK details. Тестировать утечки отдельно.
- [HTTP GET тоже расходует трафик и серверные ресурсы] → одна свежая проверка на попытку и ограниченные повторы; сокращение realtime-соединений не выдаётся за нулевую стоимость REST.
- [Гонка отмены с уже отправленным запросом открытия вкладки или записью] → передача id/generation операции до фонового обработчика, проверка до side effect, отсутствие ложного подтверждения отмены уже выполненного действия; создание не повторяется автоматически.
- [Оптимизация ломает server-read барьер] → обязательная матрица старого cache, двух порядков ответов, обрыва до/после ack, локальной навигации и поздней generation.

## Migration Plan

1. Реализовать и проверить контракты/клиент на эмуляторах, не меняя формат комнат, Rules и тариф.
2. Подготовить JSON и Hosting headers; после отдельного разрешённого этапа публикации проверить публичный статус без Auth. Приложение остаётся работоспособным и до появления файла.
3. Пересобрать release; проверить CSP, host permissions, privacy/disclosures и отсутствие секретов. Ручное управление статусом не запускает deploy Auth/Rules.
4. Выпустить расширение отдельным действием. Откат — предыдущий пакет; JSON не влияет на старую версию. Для снятия инцидента публикуется свежий `operational`.
