# Design

## Context

`cloud.mjs` и QA smoke проверяют один project ID. `loadRelease`, status/rotation scripts и часть тестов читают реальные `firebase/generations` и `firebase/control`. Клиент уже получает параметры через env; его протокол менять не требуется. См. proposal и deployment-configuration delta.

## Goals / Non-Goals

**Goals:** независимость тестов, явные операторские пути, сохранение контрактных снимков и повторяемая проверка перед публикацией.

**Non-Goals:** provisioning, deploy, новый релиз, перенос комнат или изменение безопасности Firebase.

## Decisions

- Игнорируемая `.local/deployment/` содержит `generations/` и `control/`. Публичная `config/deployment.example/` содержит согласованные вымышленные образцы. Выбран простой фиксированный путь вместо нескольких конкурирующих overrides.
- `config:init` копирует примеры и env только в отсутствующие файлы. Оператор заполняет реальные IDs явно; фиктивный инвентарь не подтверждает live-состояние. Существующие файлы сначала сохраняются локально без изменения bytes контрактов.
- QA задаёт отдельный `CLOUD_FIREBASE_PROJECT_ID`, совпадающий с backend/control env; поколение имеет `qa-` prefix. Сохраняется запрет production в общей валидации. Отчёты получают метаданные явно, а не присваивают исторический QA всем измерениям.
- Hosting использует `RELEASE_SUPPORT_EMAIL`; исходные страницы нейтральны. Email валидируется перед подстановкой.
- Unit-тесты используют fixtures, а не `.local` и не примеры production. В CI нет cloud/deploy команд.
- Встроенный scanner проверяет выбранную историю, архивы gzip, metadata и пути; дополнительные проверки известными локальными значениями выполняются при подготовке. Детерминированные тестовые secrets допускаются только в конкретном тесте scanner/package audit.
- По одобрению пользователя создаётся новая корневая main с одним коммитом. Резервная ветка остаётся только локально; local push guard не допускает отправку исходной истории. По отдельному ответу пользователя текущий email автора сохраняется в метаданных публичного коммита; это явное исключение из обезличивания документов.

## Risks / Trade-offs

- Потеря операторских данных → сначала резервная ветка и копия исходных документов/настроек в `.local`, затем замена отслеживаемых файлов.
- Ослабление QA guard → тесты совпадения роли, отказа production и неполных настроек.
- Устаревшие подтверждения после очистки → внутренний release evidence остаётся локально; публичные исторические отчёты помечены как обезличенные, хэши старых коммитов не выдаются за публичную историю.
- Резервная ветка содержит исходные сведения → явно публикуется только main, локальный guard проверяет достижимость исходного коммита.
- Scanner не доказывает отсутствие неизвестного формата → документированная граница и проверка чистого checkout; тестовые исключения узкие.

## Migration Plan

Сохранить исходный HEAD и локальные файлы, скопировать deployment bytes, перенести команды и fixtures, очистить документы, проверить чистое дерево во временном checkout, проверить production build без deploy. После проверок синхронизировать specs и архивировать только этот change. Создать один корневой коммит main; проверить отсутствие предков исходной истории и повторить scanner. Для восстановления использовать локальную резервную ветку и `.local`.

## Readiness

Ready — зависимости и перенос проверены по коду; история и границы работы явно одобрены.
