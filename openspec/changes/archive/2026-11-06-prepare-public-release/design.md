# Design

## Context

См. [proposal.md](proposal.md) — Why. `wxt.config.ts` выбирает QA cloud output по четырём `WXT_FIREBASE_*`; `scripts/cloud.mjs` всегда читает `.env.cloud` через npm scripts, генерирует облачные Rules без `_probes` и разворачивает Auth/RTDB/Hosting. Обычная сборка без Firebase отключена от сервера. Отдельного публичного пакета нет.

Hosting — статические HTML/CSS с CSP и `Referrer-Policy: no-referrer`. Bridge обрабатывает только корневую страницу приглашения и передаёт её fragment в extension-контекст; страницу privacy policy нельзя превращать в ещё одну точку входа. `room-session` уже требует бессрочных комнат и изоляции секретов.

Пользователь выбрал отдельный production-проект и сообщил издателя `briginas` и публичный email поддержки `support@example.invalid`. 2026-11-04 пользователь подтвердил существующий Chrome Web Store developer account `operator@example.invalid` и выбрал его для выпуска; по его сообщению dashboard открыт в браузере. Это подтверждение пользователя, а не результат проверки dashboard агентом. Email входа не включается в расширение или публичную privacy policy только из-за его использования для публикации. Первичная статическая проверка QA-пакета — [package-audit.md](package-audit.md).

## Goals / Non-Goals

**Goals:** одна явная release-команда, проверяемый ZIP, отдельный сервер, правдивые публичные материалы и воспроизводимый порядок выкладки.

**Non-Goals:** менять engine/адаптер, диагностировать TrustedScript или прежний Auth-сбой, выполнять широкую приёмку на разных сетях, вводить TTL/новые роли/собственный backend. Решение перейти сразу к выпуску не закрывает эти проверки и не позволяет заявлять их успех в store listing.

## Decisions

### 1. Отдельная release-конфигурация

Добавить `.env.production.example` с четырьмя публичными Firebase-параметрами и явным `RELEASE_FIREBASE_PROJECT_ID`; реальный `.env.production` остаётся вне Git. Release launcher сверяет выбранный ID с Firebase project ID, запрещает QA/demo, probe/emulator-флаги и противоречивые окружения. Разрешённые параметры передаются в WXT явно; унаследованные значения процесса не должны незаметно менять сборку. Output — отдельный `.output/release/`, QA-команды сохраняют прежнее назначение.

Начальная версия — `0.1.0`, один источник версии в `package.json`. До следующей загрузки в store версия увеличивается. Не использовать текущую `.output/cloud` как источник публичного ZIP: там могли быть QA-патчи. Альтернатива с заменой `.env.cloud` отклонена, поскольку смешивает QA и production и усложняет воспроизведение.

### 2. Свежий output и контроль пакета

Release launcher очищает только собственный output, собирает основной `src/`, проверяет manifest и перечисленные ресурсы, затем создаёт ZIP только из каталога расширения. Firebase deploy config, Rules, Hosting и отчёты остаются рядом с output, за пределами ZIP. `manifest.json` — в корне архива.

Добавить оригинальную простую иконку в векторном исходнике и PNG 16/32/48/128, указать их в manifest. Без использования фирменного логотипа YouTube. Для store 128px PNG и минимум один реальный screenshot; размеры проверяются по официальной документации на момент подготовки. Optional promo не блокирует первый выпуск.

Контроль выполняется и на распакованном ZIP: allowlist путей/расширений, отсутствие symlinks, `.env`, source maps, исходников тестов, probes, native instrumentation и localhost-разрешений. Проверять соответствие файлов manifest и согласованность production origin в runtime-конфигурации и manifest. Вычислять SHA-256 ZIP и сохранять сводку (commit, версия, публичные project/origin, команды, результаты), не включая credentials. Архив создаётся во временном имени и становится готовым release-артефактом только после всех проверок; устаревший успешный ZIP не должен маскировать ошибку нового запуска.

Сканировать известные форматы private/service-account keys и токенов, а также конкретные непубличные значения доступной конфигурации и известные QA fixture-секреты. Публичными считать только четыре точных Firebase-параметра, а не любой `WXT_*`. Разрешённый Firebase Web API key отражать как присутствующий, без значения. Сообщения об отказе содержат путь и категорию, без совпавшего текста. Отрицательные тесты подставляют синтетические секреты и доказывают остановку выпуска; статическая проверка не объявляется полной гарантией отсутствия всех возможных утечек.

### 3. Firebase для первого выпуска

Создать отдельный проект со свободным ID, зарегистрировать Web App, RTDB в `europe-west1`, включить только используемый Anonymous Auth и развернуть тот же контракт Rules без `_probes`. Начать с доступного Spark без подключения платёжного аккаунта; зафиксировать фактические лимиты плана, ожидаемую небольшую аудиторию и каналы наблюдения. Если Spark недоступен или не покрывает задачу, зафиксировать препятствие до включения платного плана; изменение биллинга требует решения владельца.

Проверить API restrictions клиентского ключа: только API, необходимые используемым Firebase-сервисам, без посторонних платных API. HTTP referrer restrictions не включать вслепую для extension origin: любое ограничение проверяется в собранном расширении, включая refresh токена. Ключ идентифицирует проект и не заменяет серверный контроль доступа. Отдельно проверить запрет корневого чтения, `_probes`, чужого presence и некорректных playback, используя существующую локальную матрицу и ограниченный production smoke. Реальные секреты и токены не записываются в traces/отчёты.

Прямой Anonymous Auth клиент с Rules не обеспечивает серверного ограничения частоты создания комнат. Для первого небольшого выпуска это явное эксплуатационное ограничение: наблюдать Auth/RTDB/Hosting usage, определить владельца реакции и порядок временного закрытия записи при злоупотреблении. Проверить применимость App Check к MV3 перед любым enforcement; нельзя включать его без работающего клиента или считать существующие Rules защитой от исчерпания квоты. Не добавлять custom backend в рамках подготовки этого релиза.

Не создавать автоматическое удаление комнат: это противоречит принятому контракту. В runbook описать бессрочное хранение последнего состояния, рост базы, административное удаление по обоснованному обращению и его влияние на всех участников. Резервирование/восстановление выбирать по фактическим возможностям текущего плана; не обещать несуществующий backup. Для Blaze отдельно требуются согласованные бюджет и уведомления; budget alerts сами по себе не ограничивают расходы.

### 4. Privacy и store materials

Подготовить `firebase/hosting/privacy.html` и постоянную ссылку на неё вне скрываемого `#installation`. Политика описывает Anonymous UID и локальные credentials, video ID, исходное название, playback/время/автора последнего действия и presence, локальный каталог с приглашениями, инфраструктуру Firebase/Google и доступ участников по полному секрету. Отдельно объяснить: выход/удаление из каталога не удаляют серверную комнату; автоматического TTL нет; видеопоток идёт от YouTube. Не заявлять, что вообще никакие данные не передаются, и не обещать возможность самостоятельного серверного удаления, которой в продукте нет.

Для store подготовить русский текст карточки, single purpose, обоснование каждого реально запрошенного разрешения и host permission, заполнение privacy disclosures по фактическим данным (в том числе identifiers/authentication information и activity, где применимо), инструкции проверки в двух Chrome profiles без учётной записи и описание ограничений. Проверить отсутствие remote hosted code: Firebase SDK bundled; сетевые JSON-данные не являются кодом. Декларации должны совпадать с финальным пакетом, а не только с намерениями плана. Дополнительные разрешения «на будущее» не добавлять.

### 5. Два этапа страницы приглашения

Подготовить статическую страницу из шаблона с публичным store URL и состоянием доступности, сохраняя DOM-контракт `#installation`. Store ID не включать в runtime Firebase-конфигурацию: он нужен только Hosting. Пока draft/review недоступен пользователям, сайт показывает ожидание публикации. После доступности карточки — рабочую HTTPS-ссылку установки и просьбу вернуться к приглашению и обновить страницу. Секрет fragment не добавляется в ссылки store/privacy; `no-referrer` сохраняется, внешняя ссылка использует `rel="noreferrer noopener"`.

Тесты проверяют страницу без расширения, с установленным расширением и privacy route без invitation iframe/Auth. Страница остаётся полезной без JS и без установленного расширения.

## Risks / Trade-offs

- [Store ID ещё не получен; доступ к dashboard не проверен агентом] → использовать выбранный аккаунт `operator@example.invalid`; при работе в открытой вкладке проверить выбранного publisher перед загрузкой. Draft upload и фактические URL остаются отдельными невыполненными шагами.
- [Новый production origin или изменение ID расширения ломает подключение] → smoke именно release-пакета на настоящем сервере; повторить после store-установки, не переносить выводы только из QA.
- [Неограниченный Anonymous signup/создание комнат расходуют квоту] → ограничения API key, мониторинг и описанная реакция; эта архитектура не обещает защиту от DDoS.
- [Сохранённые комнаты содержат сведения о просмотре] → правдивое раскрытие состава/хранения, доверенный storage расширения и отсутствие live-секретов в ZIP, screenshots и отчётах.
- [Публичный ранний выпуск имеет оставшиеся проверки] → перечислить фактические ограничения; не заявлять независимые сети, рекламу или TrustedScript проверенными.

## Migration Plan

1. Выполнить локальные задачи release tooling/материалов и проверки на изолированных fixtures. Подготовить production config и записать фактические эксплуатационные настройки.
2. Создать production-проект; развернуть Auth/Rules/Hosting с privacy и честным состоянием «ожидается публикация». QA-данные не переносить. Smoke: Auth, новая комната, приглашение/вход, общая команда, выход, повторное открытие; сохранить обезличенные результаты.
3. Собрать и проверить финальный ZIP, проверить локально в Chrome, подготовить screenshots. Получить draft item в Chrome Web Store и записать его ID. Финальную готовность разрешений/деклараций сверить с пакетом.
4. Подать на review с deferred publishing. После одобрения выполнить ручную публикацию, проверить публичную карточку и переключить Hosting на установку из store. Записать store URL, время, SHA-256 загруженного ZIP и Hosting release.
5. Проверить установку из store и возвращение по приглашению. Успешный draft upload или review не закрывает фактическую публикацию/установку.

Восстановление: хранить предыдущие версии Rules/Hosting и проверенный ZIP в доступном владельцу месте; credentials и резервные копии пользовательских данных не сохранять в Git. Hosting/Rules можно вернуть к предыдущей согласованной версии. Chrome Web Store не понижает версию установленного расширения: исправление выпускается под большей версией; при серьёзном сбое остановить распространение и показать честный статус на Hosting. В первом выпуске предыдущей production-версии нет. Изменений схемы и миграции комнат не требуется.
