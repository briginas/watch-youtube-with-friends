# Проверка DOM-адаптера YouTube

Задачи 1.4–1.5/4.4, change `youtube-sync-prototype`. Общий адаптер находится в `src/lib/player/youtube-player.ts` и используется также основной сборкой комнаты. Здесь isolated content script с диагностикой и отдельный background для управления из теста. Обе сборки включают узкий MAIN-world bridge: он применяет только скорость через внутренний `#movie_player.setPlaybackRate()`, чтобы штатные меню и клавиатура соответствовали media. Комнат, Firebase и данных доступа в MAIN нет.

```sh
nvm use
npm run test:player
npm run test:player:youtube
```

Первая команда запускает управляемую страницу с настоящим seekable HTMLMediaElement (локально сгенерированный WAV), имитируя DOM контролов YouTube. HTTP-ответ страницы перехватывается Playwright. Реклама и waiting на этом стенде синтетические, а pointer/keyboard и media-события выполняет Chromium.

Вторая команда открывает настоящий сайт в свежем временном Chromium profile без входа в аккаунт. Сначала проверяет контролы и удалённые команды. Затем отключает сеть через CDP только в тестовой вкладке, вызывает дальний seek, проверяет локальный buffering и возвращается к закэшированным 10 с после восстановления сети. Отдельный сценарий наблюдает три ролика по 10 с; при естественной рекламе проверяет отказ применения и отсутствие намерений до возврата основного видео. Если реклама не появилась, сценарий skipped, а не passed. Реклама не пропускается и не подменяется.

Live-матрица также проверяет отсутствующий ролик `00000000000`, переход по настоящей рекомендации, Back/Forward и действие «Вернуться в комнату». Проба сохраняет исходный videoId; при другом URL показывает «Не синхронизируется» и блокирует применение. Действие возврата открывает исходный watch URL с полной загрузкой страницы. Это возврат к ролику, а не восстановление комнатной сессии: room transport ещё не подключён.

`youtube-rate.spec.ts` проверяет удалённые ×1,25/×1,5/Normal в нативном меню и первое `>` после ×1,25: ожидается ×1,5 и ровно одно намерение rate, без обратного события от apply. Целевой запуск после сборки пробы: `YOUTUBE_PLAYER_REAL=1 npx playwright test --config playwright.player.config.ts youtube-rate.spec.ts`. Эта проверка требует настоящего YouTube; управляемый стенд отдельно моделирует расхождение внутренней и media-скорости, отсутствие/ошибку API и отклонение посторонних запросов bridge.

Autoplay проверяется отдельно на стенде и настоящем YouTube в свежем профиле с `--autoplay-policy=document-user-activation-required` и отключёнными MEI exemptions. Метод `play()` и media-события не подменяются. До отказа запрещены `page.evaluate()`, locator-проверки и trace snapshots: в используемом Playwright они дают странице user activation и делают тест недостоверным. Готовность читается extension messages; отсутствие activation — через CDP `Runtime.evaluate` с `userGesture: false`. В autoplay-файлах trace отключён. Ожидается настоящий `NotAllowedError`, подсказка «Нажмите play» и первый локальный запуск без исходящего намерения; следующая пауза снова создаёт намерение.

Контролируемые browser-результаты находятся в `.output/youtube-player/test-results/`, live-наблюдения — в `.output/youtube-player/live-results/`. Live-тесты сохраняют `youtube-observations.json`, `youtube-ad-observations.json` и отдельные `youtube-lifecycle.json`; при сбое также trace, кроме autoplay. Эти файлы не входят в git. В отчёте хранится компактный снимок подтверждённых наблюдений; trace с сетевыми URL не публикуется.

Для ручной проверки локальных состояний открыть недоступный ролик, затем обычный ролик и перейти по рекомендации. Индикатор должен объяснять ошибку либо показывать действие возврата. При autoplay-блокировке нажать обычный play в плеере. Проба проверяет выход адаптера `onIntent`; отсутствие записи другим участникам в настоящей комнате проверяется позднее вместе с sync engine.

## Ручная проверка рекламы

1. Выполнить `npm run build:player-probe` и загрузить `.output/youtube-player/chrome-mv3` в Chrome через «Загрузить распакованное расширение».
2. Открыть обычную watch-страницу, на которой естественно показывается реклама. Должен быть виден индикатор `Player probe: ad`, а после окончания рекламы — готовность основного ролика. Проба не меняет рекламу.
3. Для фиксации полного результата использовать opt-in browser-сценарий либо внутренние сообщения расширения из DevTools service worker. Сообщение `chrome.tabs.sendMessage(tabId, {type: 'player-probe', action: 'read'})` возвращает `status`, `sample`, `intents`, `traces`. `action: 'clear'` очищает журнал. `action: 'apply', target: {positionSeconds: 10, playbackRate: 1, isPlaying: true}` должно вернуть `blocked` во время рекламы. Полный протокол диагностики доступен только extension-контекстам; MAIN bridge обслуживает лишь setter скорости без комнатных полномочий.
4. Записать браузер, ролик, условия, состояния и результат в журнал эксперимента. Отсутствие рекламы, один визуальный индикатор или успешный mock-тест не закрывают ad-сценарий.

Окно корреляции ввода — 1500 мс, завершение seek — 120 мс после последнего события/отпускания указателя. Удалённое применение отслеживается до устойчивого совпадения или таймаута 3 с. Это локальные параметры адаптера, а не измерения задержки синхронизации между участниками.
