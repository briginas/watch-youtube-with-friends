# Работа с изменениями

1. **OpenSpec.** Перед планированием изменений ознакомься с `openspec/specs/` и прочитай спецификации, относящиеся к задаче, а также связанные активные changes. Используй их вместе с документацией и кодом как основу для анализа текущего поведения проекта. Если меняется поведение расширения, его требования или контракт между компонентами, создай или продолжи подходящий OpenSpec change. Зафиксируй ожидаемое поведение и сценарии проверки до реализации. Правки опечаток, документации, тестов или внутреннего кода можно делать без отдельного change, если требования и поведение остаются прежними. Следуй [процессу разработки](docs/development.md) и инструкциям в `.agents/skills/`.
2. **Версия расширения.** При подготовке релиза повысь версию один раз по самому существенному изменению в пакете с прошлого выпуска. Используй `patch` для исправлений и небольших улучшений, `minor` для новых обратно совместимых возможностей, `major` для намеренных несовместимых изменений. Обновляй `package.json` и `package-lock.json` вместе и подготовь дескриптор по [инструкции выпуска](docs/release.md). Совместимость с поколением backend определяй отдельно от номера версии. Для локальной проверки используй метку сборки в деталях расширения на `chrome://extensions`. Она формируется автоматически и содержит версию пакета, короткий SHA коммита и время в UTC. Пометка `dirty` указывает на незакоммиченные изменения, `no-git` — на отсутствие сведений о коммите.
3. **Changelog.** При каждом повышении версии обновляй `CHANGELOG.md` в том же коммите, что и `package.json` и `package-lock.json`. Добавляй запись новой версии в начало списка, сохраняя формат файла: номер версии, дата и краткое описание заметных изменений с прошлого выпуска. Если запись этой версии уже есть, дополни её без дублирования. Перед коммитом проверь соответствие версии в changelog обоим package-файлам. Подготовка сборки, сохранение черновика и отправка на review не означают публикацию в Chrome Web Store; указывай статус публикации только при наличии подтверждения.
4. **Сборка для Chrome.** Для ручной проверки совместного просмотра с рабочим сервером запусти `npm run release:build` с настройками из `.env.production` и укажи пользователю путь к `.output/release/chrome-mv3`. Обычный `npm run build` создаёт `.output/chrome-mv3` без настроек сервера, поэтому «Смотреть вместе» в ней недоступна. Подробности — в [инструкции выпуска](docs/release.md#сборка-и-аудит).
5. **Завершение OpenSpec.** После реализации выполни проверки и отметь выполненные задачи. Когда все обязательные проверки пройдены, синхронизируй delta specs с основными спецификациями, заархивируй change и запусти `npm run spec:validate`. Завершённый change архивируй в рамках той же задачи.
6. **Коммит.** После проверок сделай локальный коммит с файлами текущей задачи. Включи обновлённые спецификации, архив change, файлы версии и changelog, если они менялись в рамках задачи. Чужие и несвязанные правки оставь вне коммита.
7. **Публикация в Chrome Web Store.** По умолчанию отправляй релиз на review с включённой автоматической публикацией после успешной проверки (`Publish automatically after it has passed review`). Запрос «зарелизь версию» включает загрузку пакета и отправку на review с этой настройкой. Отложенную публикацию (`deferred publishing`) выбирай только по явной просьбе пользователя. Перед отправкой проверь состояние галочки; в результате отдельно укажи статус review и включена ли автопубликация. До подтверждения Store не называй версию опубликованной.
